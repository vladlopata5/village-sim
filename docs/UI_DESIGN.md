# VillageSim — спецификация пользовательского интерфейса

## 1. Статус, назначение и границы документа

Дата: 2026-10-13. Исходная спецификация: `5244087ddc723a2d5beca176f6b6f99f47ce9e51`. Актуализация включает окончательно согласованные решения Q1–Q9. Проверенная база игровых API остаётся `e8fdb43ca380e8d31971c89173fd776e55f63ef4`: эта задача изменяет только документ.

Это единая целевая спецификация нового UI для канонической сцены `scenes/main_3d.tscn`. Она описывает согласованное поведение будущего интерфейса, а не утверждает, что этот интерфейс уже реализован. В рамках подготовки документа UI, сцены, скрипты, ресурсы и игровые механики не изменяются.

Документ согласован с актуальными решениями [DECISIONS.md](DECISIONS.md), [GAME_DESIGN.md](GAME_DESIGN.md) и [ROADMAP.md](ROADMAP.md). Исторические описания прототипа в этих документах не следует считать описанием нового UI. Текущие источники данных перечислены в разделе 13, согласованные решения Q1–Q9 и отложенная проработка — в разделе 14.

Основные ограничения:

- Интерфейс отображает симуляцию и вызывает её существующие API. Он не рассчитывает производство, потребности, перевозки или строительство самостоятельно.
- Новые кнопки и вкладки появляются только для реально доступных функций. Единственное согласованное исключение первой версии — видимая неактивная кнопка «Демонтировать» во вкладке «Инфо» здания; она ничего не выполняет. Остальные будущие возможности описываются как направление развития, без фиктивных данных и неработающих кнопок.
- Не меняются баланс, ресурсы, строительные рецепты, правила назначений, вместимость, резервирования, расписание и committed-action semantics.
- UI развивается прежде всего для `main_3d`. Legacy `scenes/main.tscn` и общая Simulation/Domain не объявляются устаревшими вместе с заменяемым интерфейсом.
- Обязательная информация видна непосредственно в карточках, списках и сообщениях. Всплывающая подсказка не может быть единственным способом узнать название, стоимость или причину отказа.

## 2. Общая композиция

Интерфейс накладывается на игровой мир. Основные области:

| Область | Положение | Назначение |
|---|---|---|
| Лента сообщений | Сверху слева | Реплики жителей, игровые уведомления и важные события |
| Время | Сверху справа | Игровой день, время, пауза и скорости симуляции |
| Зелёная панель | Снизу слева | Основные действия игрока, вкладки и быстрый доступ |
| Синяя панель | Снизу справа | Информация о выбранном объекте или выбранном типе постройки |

Дополнительно используются обычные окна быстрого доступа и полноэкранные окна.

Открытие, закрытие, раскрытие и сворачивание UI не меняют позицию, ориентацию или масштаб камеры. Интерфейс не уменьшает игровой viewport, чтобы освободить место для панелей. Переход по имени или событию меняет выделение, но не центрирует камеру автоматически.

Зелёная и синяя панели независимы. Выбор объекта не сворачивает зелёную панель; обычное переключение её вкладок не раскрывает и не сворачивает синюю. Явные связанные переходы описаны в разделах 3 и 8: выбор типа постройки очищает выделение, а сворачивание «Строительства» при активном размещении отменяет инструмент и возвращает синюю панель в пустое состояние.

Синяя панель имеет свою область справа даже в развёрнутом состоянии. Обычные окна размещаются вне этой области и не перекрывают карточку. Их размеры и положение не зависят от степени раскрытия карточки. Первоначальный ориентир компоновки — **1920×1080**; будущий макет обязательно проверяется также на **1600×900**. Точные пиксельные размеры, отступы, UI scale и минимальное поддерживаемое разрешение определяются при разработке макета и проверяются фактически, а не задаются сейчас. Нельзя решать нехватку места сдвигом камеры или нарушением этих правил.

## 3. Зелёная панель основных действий

### 3.1. Единый ряд кнопок

В нижней части панели находится единый ряд кнопок двух визуально различимых типов:

| Тип | Действие | Пример |
|---|---|---|
| A — вкладка | Открывает содержимое внутри зелёной панели | «Строительство» |
| B — быстрый доступ | Открывает отдельное окно | «Жители»; «Журнал» после появления его функциональности |

Различие должно быть заметно по оформлению и состоянию кнопки, а не только по её подписи или tooltip.

### 3.2. Поведение вкладок

- Нажатие неактивной вкладки открывает её содержимое.
- Выбор другой вкладки заменяет текущее содержимое; два раздела одновременно не раскрываются.
- Повторное нажатие активной вкладки сворачивает панель до ряда кнопок.
- Сам ряд кнопок остаётся доступным в свёрнутом состоянии.
- Открытие окна кнопкой типа B не заменяет содержимое активной вкладки.

Если вкладка «Строительство» сворачивается во время активного размещения здания, placement отменяется без подтверждения постройки. Синяя панель возвращается в пустое компактное состояние с игровым днём, зелёная — к ряду кнопок. Это согласованный связанный переход, а не случайное прохождение клика в мир.

### 3.3. Расширяемость

Кнопки и разделы регистрируются через общую структуру описаний: стабильный идентификатор, вид кнопки, название, доступность и связанное содержимое либо окно. Это UI-описания, не реестр игрового состояния.

Количество элементов не зашивается в основной код меню. При большом количестве кнопок необходимы прокрутка или компактное расположение, сохраняющие доступ к названиям и различимость двух типов. Конкретный вариант выбирается при настройке макета.

Сейчас допускаются только работающие функции. «Экономика», «Квесты», «Приоритеты» и другие будущие разделы не добавляются для заполнения ряда. Существующие дороги должны сохранить доступность при будущей замене строительной панели; новый road workflow не вводится.

## 4. Синяя информационная панель

### 4.1. Состояния содержимого

| Состояние | Содержимое |
|---|---|
| Нет выделения и нет выбранного типа постройки | Небольшая карточка с номером текущего игрового дня |
| Выбран житель | Карточка жителя |
| Выбрано здание, включая стройплощадку | Карточка соответствующего BuildingInstance |
| Активен выбор типа для placement | Информация о BuildingDefinition выбранной постройки |

Панель полностью не исчезает. Погода и события в пустом состоянии — только возможное будущее расширение; сейчас эти поля не создаются.

Выбранный тип ещё не размещённой постройки не является фиктивным BuildingInstance. Это состояние инструмента строительства, при котором обычное выделение очищено.

### 4.2. Компактный и развёрнутый режимы

При первичном выборе объекта открывается компактная карточка. Игрок может вручную развернуть её вверх для подробностей и вкладок, затем свернуть обратно. Развёрнутая карточка может занимать значительную часть высоты экрана; длинное содержимое прокручивается внутри неё.

При переключении между жителями и зданиями степень раскрытия сохраняется. Она принадлежит синей панели, а не отдельному объекту. Если у новой карточки есть ранее активная вкладка, она сохраняется; иначе открывается основная вкладка: «Био» для жителя, «Инфо» для здания. Не показывается пустая вкладка только ради сохранения её идентификатора.

При полном снятии выделения панель возвращается в пустое компактное состояние с игровым днём; память раскрытия объекта сбрасывается. После этого новый выбор жителя или здания начинается с компактной карточки. Это не меняет сохранение раскрытия при непосредственном переключении между выбранными объектами. Конкретная компоновка предпросмотра типа постройки определяется при разработке макета, без изменения камеры.

## 5. Карточка жителя

### 5.1. Компактный режим

Набор первой версии: имя, профессия, настроение, возраст и текущая деятельность. HP не входит в требования первой версии и не отображается.

Имя, профессия, настроение, возраст и деятельность уже имеют источники в ResidentData. Настроение отображается из существующего значения, без придумывания новых причин или эффектов. HP не добавляется в ResidentData ради интерфейса; фиктивное «100/100» запрещено.

Здоровье/HP остаётся возможным будущим сведением и отдельной игровой механикой, требующей собственного проектирования. Портрет и индикаторы критических состояний также могут быть добавлены позднее. Сейчас не требуются новые ассеты и не создаются новые статусы.

### 5.2. «Био»

- Потребности: голод, усталость, социальная потребность и досуг. Значения читаются из существующей модели Need; направление шкал не переопределяется UI.
- Черты характера.
- Предпочтения и антипатии. Сейчас это предпочтения к чертам других жителей, а не новая система любимой еды, погоды или занятий.
- Назначенный дом и возможность назначения либо смены через существующие механизмы housing. Отсутствие дома отображается честно; временное размещение в городском центре не подменяет постоянный `home_location_id`.
- Сворачиваемый личный дневник за текущий игровой день.

Дневник фильтрует существующие записи по игровому дню `created_minute`. UI не удаляет старые KEY-записи и не меняет утреннее истечение TEMPORARY. Пустое состояние сообщает об отсутствии записей за день. Не требуется создавать запись для каждого произошедшего события: существующая запись в дневнике может быть вероятностной.

### 5.3. «Работа»

- Профессия и закреплённое рабочее место.
- Смена профессии и рабочего места через PlayerControl.
- Для поддерживаемых профессий — существующее назначение независимой рабочей области, повторное использование области и снятие назначения.
- Текущая рабочая задача отдельно от общей деятельности: например, движение к источнику, погрузка, доставка, рубка или строительство, если соответствующий controller предоставляет состояние.
- Сворачиваемый список навыков с вычисляемыми уровнями; XP можно показывать компактно. UI не хранит level отдельно и не вводит skill bonuses.
- Доступные приказы, существующие поручения и их отмена, когда предусмотрены соответствующим API. Не обещается отмена любого автономного действия одной общей кнопкой.

Профессия, назначение и committed task могут временно различаться. Например, переназначенный Porter уже имеет новое рабочее здание, но завершает старую безопасную перевозку. Карточка должна показывать это состояние, а не перенаправлять рейс ради визуального совпадения.

Porter без назначения отображается как «Носильщик без рабочего места». У свободного лесоруба или каменодобытчика показывается рабочая область. У Builder отсутствие здания не означает отсутствие доступной работы: действует текущий world-work workflow.

### 5.4. «Отношения»

- Список существующих известных отношений с другими жителями.
- Значение направленного отношения выбранного жителя к каждому собеседнику.
- Имя другого жителя является действием перехода: выбор через общий selection и открытие его синей карточки, без движения камеры.

Отношения A→B и B→A не объединяются в одно симметричное значение. UI не создаёт neutral records ради заполнения списка и не выводит «дружбу» либо «семью» из числового opinion. Семья и родословная остаются будущим расширением. Переход доступен только к существующему зарегистрированному жителю; отсутствие связанного объекта не должно приводить к ошибке.

## 6. Карточка здания

### 6.1. Компактный режим

- Название и тип.
- Текущее состояние: строится, работает, простаивает и другие подтверждённые состояния.
- Занятость производственных рабочих мест, если эта категория применима.
- Занятость логистических мест Porter, если они предусмотрены.
- Текущая деятельность или причина простоя, если такие сведения доступны.

`BUILT` означает завершённое строительство, а не обязательно активную работу. UI не должен объявлять здание работающим только по lifecycle. При отсутствии данных об активности достаточно достоверного «Построено»; причина простоя не придумывается.

### 6.2. «Инфо»

- Общие характеристики, доступные в BuildingDefinition/BuildingInstance.
- Работники по именам, отдельно по производственным функциям и по роли Porter.
- Занятые и свободные места в каждой категории.
- Текущие посетители, если применимо и есть источник.
- Для HOME — жильцы и управление заселением.
- Назначение и освобождение работников через существующие механизмы.
- Переход по имени работника или жильца к его карточке.
- В нижней части — отдельная видимая, но неактивная кнопка «Демонтировать» согласно правилу ниже.

Назначенные сотрудники — это ResidentData, а не occupants физических WORKER/COURIER markers. Посетители и текущая занятость слотов показываются отдельно и не уменьшают кадровые лимиты. Строители стройплощадки не становятся постоянными производственными работниками этого здания.

Для существующей неограниченной производственной вместимости отображается её фактическая семантика, а не «0 свободных». Нулевая `porter_capacity`, напротив, запрещает назначение Porter. Отсутствующая категория не получает пустой список и кнопку назначения.

**Кнопка «Демонтировать» в первой версии.** Она присутствует во вкладке «Инфо» развёрнутой карточки здания, видима и неактивна. Нажатие ничего не делает; окно подтверждения удаления пока не требуется и не открывается.

Кнопка не подключается к `Main3D.cancel_construction`, `LogisticsController.remove_building`, unregister или другим частичным API. Удаление готовых зданий не реализуется, материалы не возвращаются. В дальнейшем кнопка будет связана с полноценной механикой демонтажа, которая проектируется отдельно. Это явное исключение из запрета неработающих кнопок, а не объявление частичного удаления готовой функцией.

### 6.3. «Производство»

Показывается при наличии соответствующих данных/возможностей:

- Производимый ресурс или рецепт.
- Необходимые входные материалы.
- Текущие входящие и выходящие запасы.
- Прогресс работы.
- Причина простоя, если предоставлена системой.
- Дополнительные действия только для реализованных механизмов.

Входящие и выходящие запасы здесь означают фактические input/output buffers, а не новые настройки flow и не inbound/outbound reservations. Производственные здания не получают дополнительную вкладку «Склад» исключительно ради своих буферов. Добывающие здания не получают выдуманный рецепт переработки.

### 6.4. «Склад»

Показывается только у зданий полноценного хранения и логистики, сейчас — Warehouse/Storage и Town Center (`definition.is_storage`).

Для каждого поддерживаемого ресурса отдельная строка:

| Сведения | Источник |
|---|---|
| Название | Существующий каталог ResourceType |
| Фактическое количество | `ResourceContainer.get_amount(resource)` |
| Максимальная вместимость этого ресурса | `ResourceContainer.get_capacity(resource)` |
| Индикатор заполнения, опционально | Эти же amount и capacity |

Количество не уменьшается на `reserved_out`; `reserved_in` не изображается как уже доставленный ресурс. Резервы в этой вкладке не отображаются. Вместимость остаётся отдельной для FOOD, LOG, PLANK, STONE и будущих поддерживаемых типов. Общая вместимость здания вместо per-resource capacities запрещена.

Не добавляются настройки ввоза/вывоза, минимальных запасов, production limits и другие несогласованные механики. Наличие вкладки не открывает запрещённые внешние перевозки.

### 6.5. UNDER_CONSTRUCTION

Показываются состояние строительства, необходимые и уже доставленные материалы, накопленный прогресс и другие существующие сведения стройки. Неприменимые производственные и складские вкладки скрыты.

Construction ledger принадлежит BuildingInstance. Карточка отражает incremental contribution по simulation time, сохранённый вклад после interruption и немедленное completion. UI не рассчитывает отдельный прогресс по реальному времени.

После перехода в BUILT набор вкладок обновляется по реальным возможностям того же объекта. Если активная вкладка более неприменима, выбирается основная. Существующая отмена стройки остаётся отдельным lifecycle, без возврата ресурсов; неактивная кнопка «Демонтировать» к ней не подключается.

## 7. Универсальное окно «Жители»

### 7.1. Открытие и размещение

Это одно окно без отдельного режима выбора работника. Открывается из зелёной панели, карточки городского центра и кнопок назначения работников в карточках зданий. При выбранном здании строка жителя открывает небольшой диалог назначения поверх того же окна; сам список не превращается в отдельный worker picker. Точки открытия могут предустанавливать фильтры и сортировку.

Окно имеет заранее определённые фиксированные размеры и находится ближе к центру со смещением влево. Даже полностью раскрытая синяя карточка не перекрывается. Размеры и положение окна не меняются при её раскрытии.

Открытие не снимает выделение, не сворачивает синюю карточку и не перемещает камеру. Выбор другого здания на карте оставляет окно открытым и меняет контекст его действий на новое текущее выделение.

### 7.2. Список, поиск и фильтры

Показываются все зарегистрированные жители из PlayerControl, независимо от позиции, нахождения внутри здания, сна или текущей работы. Таблица прокручивается.

Столбцы: имя, текущая профессия, рабочее место. Независимая область тоже является назначенным местом работы и показывается как область, а не как отсутствие назначения.

Фильтры:

- Поиск по имени.
- Текущая профессия.
- Доступная для назначения профессия.
- Занятость: все / с рабочим местом / без рабочего места.

Фильтр занятости относится к назначению, а не к текущему WORK/IDLE или наличию HaulJob. Не вводятся фильтры точного возраста и другие избыточные ограничения. Builder может иметь рабочую задачу и одновременно не иметь закреплённого места; это не повод подменять значение поля.

Фильтр «Доступная профессия» означает пригодность жителя к профессии в принципе, независимо от его текущей профессии и вместимости конкретного здания. **Пригодность жителя к роли и свободное место в конкретном здании — разные проверки.** Отсутствие свободных мест не ограничивает список жителей заранее: причина отказа показывается у применимой роли в диалоге назначения. Не вводятся новые квалификационные или возрастные требования. Если для фильтра нужен отдельный read-only query, его подготовка на основе существующих правил является требованием к будущей реализации; сейчас API не добавляется. Пригодность нельзя проверять пробным назначением с последующим rollback.

### 7.3. Сортировка

Доступны имя, возраст и занятость, для каждого — прямой и обратный порядок. По умолчанию список сортируется по имени.

При открытии из кнопки назначения в карточке здания можно предустановить подходящий фильтр доступной профессии и сортировку, показывающую жителей без закреплённого места первыми. Это настройка того же универсального окна; фильтр не исключает жителя из-за заполненности выбранного здания.

### 7.4. Выбор жителя и диалог назначения

Если здание не выбрано, нажатие на строку жителя выбирает его через общий selection и показывает его синюю карточку.

Основной сценарий при выбранном здании:

1. Игрок выбирает здание на карте.
2. Открывает универсальное окно «Жители».
3. Нажимает на строку конкретного жителя.
4. Открывается небольшой диалог назначения. Например: **«Назначить Степана на работу в здание „Лесопилка“?»**

Диалог не снимает выделение здания и не меняет состояние его синей карточки. Он заменяет прежний сценарий контекстного меню: ниже заголовка находятся варианты назначения по применимым профессиям и кнопка «Отмена».

### 7.5. Применимые роли и доступность

Показываются только профессии, применимые к выбранному зданию. Например, у лесопилки — производственный работник лесопилки (Пильщик) и Носильщик; каменодобытчик, собиратель и другие несвязанные профессии не показываются.

- Применимая и доступная роль имеет активную кнопку назначения.
- Применимая, но сейчас недоступная роль остаётся в списке с неактивной кнопкой и видимой причиной отказа.
- Отсутствие свободных мест — одна из причин, но не единственная; проверяются текущие игровые правила, состояние здания и capacity.
- Причина видна в диалоге, не только в tooltip.
- Новые возрастные, квалификационные и иные требования к профессиям не вводятся.

Для дома аналогично предлагается применимое действие заселения через существующий housing API. Заселение не является профессией и не меняет её под видом рабочей роли. Если действие сейчас недоступно, показывается причина по текущим правилам housing.

### 7.6. Выполнение и отмена

Нажатие активной кнопки назначает жителя на явную роль через существующий `PlayerControl.assign_workplace` либо выполняет заселение через существующий housing API. Отдельного подтверждения смены профессии после выбора роли не требуется.

Непосредственно перед выполнением повторно проверяются актуальные resident/building, допустимость роли и свободные места; для заселения — соответствующие housing checks. Нельзя выполнять действие по устаревшему контексту прежнего здания.

После успеха:

- Диалог закрывается.
- Окно «Жители» остаётся открытым.
- Выделение здания и его открытая синяя карточка сохраняются.
- Таблица жителей и сведения о персонале либо жильцах обновляются.

При отказе из-за изменившихся условий игровое состояние не повреждается, прежнее назначение сохраняется, а причина отказа отображается. Кнопка «Отмена» закрывает только диалог, не окно «Жители», не карточку здания и не выделение.

Выбор другого здания непосредственно на карте не закрывает окно «Жители»: последующие назначения относятся к новому зданию. При исполнении диалог обязан учитывать актуальность контекста, не назначать незаметно в прежнее либо другое здание. Окно не перекрывает синюю панель и самостоятельно не меняет её раскрытие.

## 8. Меню строительства

### 8.1. Каталог

Находится внутри раскрытой зелёной панели. Здания представлены плитками с изображением и постоянно видимым названием. Описание и стоимость не прячутся в tooltip.

Каталог и возможные категории расширяются на основе данных зданий. Категории не требуют фиксированного количества плиток. Показываются только реально buildable типы; Town Center сейчас не является доступной игроку постройкой.

Текущие типы: Home, Warehouse, Kitchen, Gatherer Hut, Lumberjack Hut, Sawmill и Quarry. Стоимость читается из актуальной BuildingDefinition, а не копируется из исторического текста документа. Отдельные изображения/описания и группировка каталога ещё требуют UI-подготовки; в этой задаче ассеты не создаются.

### 8.2. Выбор и предпросмотр

При нажатии плитки:

1. Снимается выделение прежнего объекта.
2. Синяя панель показывает выбранный тип: название, назначение, необходимые ресурсы, размер занимаемой территории и рабочие места, если применимо.
3. Включается существующий placement с ghost, grid snapping и проверками допустимости.

Стоимость выводится по типам ресурсов рецепта — LOG, STONE, PLANK и другим действительно предусмотренным ресурсам. Размер берётся из physical footprint в build cells, с корректным world scale; старые 2D visual dimensions не становятся физическими размерами. BuildGrid и NavigationGrid остаются отдельными системами с текущим шагом 0.5 world unit, bridge сохраняет 25 simulation units = 1 world unit.

Поворот клавишей `R` сохраняется: 90° increments, те же occupied cells и geometry. Подсветка valid/invalid и confirm-time checks, включая runtime placement blockers и entrance zones, сохраняются. Нехватка ресурсов не запрещает создание стройплощадки, если действующие placement rules это допускают. UI не добавляет проверку складских запасов поверх domain validation.

### 8.3. Последовательное размещение и выход

После успешного placement режим остаётся активным для ещё одного здания того же типа **с сохранением выбранной ориентации**. Например, после поворота лесопилки на 90° следующая лесопилка предварительно отображается с тем же поворотом. Механика `R` и геометрические проверки сохраняются. Каждое подтверждение создаёт настоящий новый BuildingInstance UNDER_CONSTRUCTION через существующий путь, без дублирующей UI-модели и без обхода validation.

Выход: `Esc`, ПКМ либо повторное нажатие активной плитки. `Esc` отменяет инструмент только после обработки более приоритетных окон по разделу 12.4. Нажатие другого типа сразу переключает постройку. После выхода синяя панель возвращается в пустое компактное состояние; зелёная панель автоматически не сворачивается.

Дополнительно сворачивание зелёной вкладки «Строительство» при активном placement отменяет размещение, возвращает синюю карточку к игровому дню и сворачивает зелёную панель до ряда кнопок. Такое действие не подтверждает стройку и не создаёт BuildingInstance.

Это целевое отличие от текущего одноразового `BuildingPlacement.confirm`, который очищает selected_definition. При будущей реализации требуется минимально связать последовательный UX с существующим lifecycle, не переписывая строительство. В этой документационной задаче поведение confirm и rotation в коде не меняется; последовательное размещение с сохранением ориентации является требованием к будущей реализации.

## 9. Окна быстрого доступа и полноэкранные окна

- Одновременно открыто не более одного обычного окна быстрого доступа.
- Нажатие кнопки уже открытого окна закрывает его.
- Открытие другого обычного окна заменяет предыдущее.
- Размеры и положения заранее определены; синяя карточка не перекрывается даже при полном раскрытии.
- Обычные окна независимы от выбора объекта и состояния зелёной панели.
- Само открытие отдельного окна не включает паузу и не меняет скорость.

Полноэкранное окно временно скрывает обычный интерфейс. После закрытия восстанавливаются прежние UI-состояния. Симуляция продолжает работать согласно текущей паузе/скорости, если игрок сам их не изменил. Восстановление не возвращает устаревшие игровые данные: исчезнувший объект нельзя заново выбрать из старого UI-снимка.

Централизованный владелец состояния окон обеспечивает эти правила, но не создаёт новый scheduler или общий игровой manager. Диалог назначения — отдельный верхний слой над обычным окном, не второе окно быстрого доступа. Порядок обработки Esc закреплён в разделе 12.4; конкретные сцены и связи координатора определяются отдельным архитектурным аудитом и планом внедрения.

## 10. Сообщения, журнал и личный дневник

### 10.1. Лента сверху слева

Показывает сообщения жителей, игровые уведомления и важные события из существующих источников. Новые сообщения появляются сверху. Через некоторое игровое или реальное время они исчезают; конкретные интервалы и основание таймера выбираются при настройке UI.

Важные непрочитанные уведомления сохраняются в счётчике после исчезновения визуальной строки. Удаление строки из ленты не означает «прочитано». Журнал и непрочитанные уведомления — согласованные будущие части UI, реализуемые отдельным этапом после подготовки настоящего источника данных. Сейчас счётчика и общего источника нет; фиктивное состояние прочтения и неработающие кнопки не создаются.

Текущий SocialFeed — кратковременное представление social output. Новый layout и порядок строк не меняют SocialEvent mechanics, RNG, вероятность narrative/diary, мнение жителей или игровой лог. Не каждый лог AI/NEED/LOGISTICS автоматически становится пользовательским уведомлением.

### 10.2. Общий журнал

Открывается из индикатора уведомлений либо кнопкой быстрого доступа, **когда функциональность реализована**. До этого соответствующие кнопки не добавляются.

- История сообщений и событий группируется по игровым дням.
- Важные уведомления можно отметить прочитанными.
- При существующей связи с жителем или зданием событие позволяет выбрать объект и перейти к его карточке.
- Переход не перемещает камеру автоматически.
- Отсутствующая связь или удалённый объект не превращаются в фиктивную сущность.

Сейчас Feed не хранит общий долговечный журнал и публикует текст без полноценного event-link контракта. DiaryEntry содержит text, importance и created_minute, но не универсальные object references. Источники и метаданные истории подготавливаются в отдельном этапе реализации журнала; UI не восстанавливает их путём разбора имён в строках и не генерирует новые игровые события ради заполнения окна. Личный дневник остаётся отдельной существующей функцией.

### 10.3. Личный дневник

Находится в сворачиваемом разделе «Био» и показывает существующие записи только выбранного жителя за текущий игровой день. Он не заменяется общим журналом и не становится психологической memory system. Существующая retention policy остаётся неизменной.

## 11. Время и отладочный интерфейс

Компактный блок сверху справа содержит номер игрового дня, время, паузу и доступные скорости. Сейчас GameTime поддерживает x1, x2, x4, x10 и x20. Список читается из существующего API, а не из отдельной UI-таблицы. Пауза использует штатный механизм.

Календарная дата с месяцем/годом не вводится: текущая модель предоставляет номер дня и HH:MM. Блок не перегружается debug telemetry, списками jobs, reservations или navigation counters.

Существующий developer UI по `F10` сохраняется с текущими ограничениями debug build. Отдельная видимая кнопка открытия F10 в основном интерфейсе не добавляется. Новый UI не заменяет его и не открывает debug actions в release.

## 12. Архитектурные требования к будущей реализации

### 12.1. Ответственность и состояния

Разделены три независимых UI-состояния: активная вкладка зелёной панели/её раскрытие; содержимое, раскрытие и вкладка синей панели; открытое обычное либо полноэкранное окно. Координатор связывает только явно описанные переходы.

Единственный источник выбранного игрового объекта — существующий ResidentSelection с selected_entity/selected_resident/selected_building. Карточки и списки читают его и меняют через select/select_building/clear. Второй независимый selection не создаётся. Placement type читается из состояния инструмента, а не записывается как выбранный resident/building.

UI сохраняет только представление: вкладки, раскрытие, поиск, фильтры, сортировку и позицию прокрутки. ResidentData, BuildingInstance, ResourceContainer и controllers остаются владельцами данных и действий. Назначенные работники и свободные места вычисляются существующими queries; UI не содержит второй mutable personnel registry.

### 12.2. Доступные вкладки и действия

Набор строится по возможностям объекта и lifecycle, с устойчивыми идентификаторами. Пустые и неприменимые вкладки не отображаются. Реализованное применимое действие может быть недоступным с видимой причиной. Единственное явное исключение для ещё не реализованной функции — неактивная «Демонтировать» во вкладке «Инфо»; другие несуществующие действия не показываются как обычные кнопки.

Если у поля нет достоверного источника в симуляции, оно не получает выдуманное значение или фиктивное состояние. Поле либо действие при необходимости скрывается с возможностью добавить его позже. Новые механики ради заполнения UI не создаются: это относится к HP, универсальным причинам простоя, семье и дополнительным производственным настройкам.

Добавление раздела не требует переделки основного меню. Это не требование большой универсальной иерархии карточек: достаточно простого общего описания UI-разделов и локальных компонентов.

### 12.3. Актуализация данных

Подписки на существующие selection, roster, assignment, needs, skill, traits, preferences, relationships, diary, resource, construction и clock signals обновляют соответствующие части интерфейса. При смене объекта старые подписки отключаются. Где отдельного события нет, допустим небольшой контролируемый refresh видимых значений; тяжёлый список не перестраивается каждый rendered frame.

Перед изменяющим действием повторяются domain checks. UI не считает старое enabled-состояние разрешением на рабочее назначение, заселение или placement. Кнопка «Демонтировать» в первой версии вообще не исполняет изменяющее действие. Удаление объектов и переход UNDER_CONSTRUCTION→BUILT безопасно обновляют доступные вкладки, ссылки и контекст окна.

### 12.4. Input и камера

Клики по кнопкам, меню, прокрутке, подтверждениям и непрозрачным интерактивным областям потребляются UI. Они не должны проходить в мир как selection, MOVE_TO, road stroke, placement или подтверждение рабочей области. Drag/release над UI не продолжает линию дороги через закрытую интерфейсом область.

Активные building/road/work-area/debug tools сохраняют существующую взаимную исключительность. Новый UI не запускает два инструмента одним кликом. Ввод текста в поисковую строку не запускает игровые горячие клавиши.

**Одно нажатие `Esc` выполняет только одно действие**, в следующем порядке:

1. Закрыть верхнее окно подтверждения или контекстный диалог, включая диалог назначения.
2. Если верхнего диалога нет — закрыть обычное окно быстрого доступа.
3. Если таких окон нет — отменить активный инструмент работы с миром, например размещение здания.

Обработанное событие не проходит к следующему уровню. Нельзя одним нажатием закрыть несколько окон, отменить placement и изменить выделение. Эти правила не вводят подтверждение для неактивной «Демонтировать».

Существующие screen-relative WASD/стрелки, MMB grab-map pan и wheel zoom сохраняются. MMB не создаёт gameplay actions. Прокрутка таблиц и окон не масштабирует одновременно камеру; события scroll/drag конкретного Control и камеры не исполняются одновременно. Существующее управление камерой и инструментами сохраняется. Показ интерфейса сам по себе никогда не меняет transform/zoom камеры.

### 12.5. Совместимость с симуляцией

Назначение использует PlayerControl и явную profession для многоролевого здания; жильё — существующий housing API; приказы — PlayerCommand/ResidentAssignment; размещение — существующий placement; производство и перевозки только отображаются.

Интерфейс сохраняет committed work, safe hauling после переназначения, owned reservation cleanup, per-resource capacity, construction timing и действующие ограничения удаления. Нельзя упростить эти правила ради карточки, фильтра или кнопки. Доступность роли не проверяется пробным assign с последующим rollback.

## 14. Согласованные решения Q1–Q9 и отложенная проработка

Q1–Q9 закрыты решениями пользователя. Отсутствующие механики и будущие задачи не являются повторным запросом согласования этих решений.

| ID | Окончательное решение | Соответствующие разделы |
|---|---|---|
| Q1 — демонтаж | Во вкладке «Инфо» видима неактивная «Демонтировать»: без действия, подтверждения, частичных API и возврата материалов. Полная механика проектируется отдельно | 1, 6.2, 12.2, 15 |
| Q2 — HP | Не добавлять в ResidentData и не отображать в первой версии. Здоровье — будущая отдельно проектируемая механика | 5.1, 12.2, 15 |
| Q3 — назначения | Строка жителя при выбранном здании открывает диалог только применимых ролей; недоступные роли видимы с причиной. Recheck перед PlayerControl/housing, сохранение обычного окна и building card; фильтр пригодности независим от capacity, read-only query при необходимости позже | 7, 12.3, 15 |
| Q4 — журнал | Журнал и unread — будущий отдельный этап с настоящим источником; нет фиктивных событий, прочтения и кнопок. Личный дневник сохраняется отдельно | 10, 15 |
| Q5 — размеры | Ориентир 1920×1080, обязательная проверка 1600×900; фиксированные обычные окна не перекрывают раскрытую карточку и не влияют на камеру. Точные размеры/scale/minimum определяются фактически позже | 2, 7.1, 9, 15 |
| Q6 — строительство | Последовательные копии сохраняют ориентацию; сворачивание «Строительства» отменяет placement без подтверждения, сворачивает зелёную панель и возвращает синюю к игровому дню | 3.2, 8.3, 15 |

| Q8 — ввод | Esc: верхний диалог → обычное окно → инструмент, ровно одно действие. Нет click-through, scroll+zoom и hotkeys при вводе поиска; controls сохраняются | 12.4, 15 |
| Q9 — сведения | Только достоверные данные; отсутствующие поля/действия при необходимости скрыты с возможностью расширения. Нет фиктивных состояний или новых механик ради UI, кроме явно оговорённой неактивной кнопки Q1 | 5, 6, 12.2, 15 |

**Действительно отложенные параметры макета:** точные пиксельные размеры и позиции, UI scale, минимальное поддерживаемое разрешение, конкретная компоновка предпросмотра типа постройки, изображения/категории каталога и вариант размещения длинного ряда кнопок. Они определяются на этапе разработки макета с фактической проверкой 1920×1080 и 1600×900; числовые параметры не придумываются в этом документе.

Интервалы исчезновения сообщений и использование игрового либо реального таймера остаются настройкой будущей ленты. Источник/хранение общего журнала и полная механика демонтажа проектируются отдельными задачами. Возможный read-only query пригодности профессии и read-представления доступных рабочих сведений относятся к будущему архитектурному аудиту и реализации, не к новой игровой политике.

Календарная дата, здоровье, погода, семья, родословная, портреты и новые игровые разделы остаются будущими возможностями. Их отсутствие не блокирует первую UI-версию и не разрешает создавать фиктивные значения. Новых существенных противоречий согласованных решений с ограничениями документа не выявлено.

## 15. Проверка полноты и критерии будущей UI-приёмки

Этот список предназначен для будущей реализации. Он не означает, что UI-тесты уже выполнены в документационном коммите.

1. Все четыре основные области расположены согласно разделу 2; будущий макет проверен на 1920×1080 и 1600×900. Размеры обычных окон фиксированы относительно раскрытия синей панели, перекрытия нет; UI не меняет camera transform/zoom.
2. Два типа зелёных кнопок различимы; вкладка переключается/сворачивается; длинный ряд остаётся доступным.
3. Синяя панель видна без выделения. Переключение объектов сохраняет compact/expanded и применимую вкладку; иначе выбирается основная. После полного clear показан компактный игровой день, следующий новый выбор начинается компактно.
4. Resident «Био», «Работа», «Отношения» читают реальные данные; HP не отображается и не добавляется в ResidentData; другие сведения без источника не подставляются. Переход по имени не двигает камеру.
5. Building показывает отдельные staffing counts, применимые вкладки, реальные production buffers и per-resource storage amount/capacity без reservations.
6. Стройплощадка отображает delivered/required и incremental progress; после completion меняются возможности того же объекта.
7. Окно «Жители» содержит всех зарегистрированных жителей, поддерживает перечисленные фильтры/сортировку и не перекрывает карточку.
8. Из кнопки назначения открывается то же окно «Жители». При выбранном здании строка открывает диалог только применимых ролей: доступные активны, недоступные видимы с причиной. Capacity не ограничивает список жителей; recheck перед назначением сохраняет прежнее состояние при отказе. Для дома заселение использует housing API, не профессию.
9. Выбор другого здания на карте сохраняет окно и меняет контекст последующих назначений. Успех закрывает только диалог, сохраняет окно и building selection/card, обновляет таблицу и персонал/жильцов. «Отмена» закрывает только диалог.
10. Каталог использует видимые изображения/названия; цена и характеристики доступны без tooltip; selection очищается при выборе типа.
11. Placement повторяется с выбранной ориентацией, переключает тип и сохраняет R/grid/blocker/geometry checks. Esc с учётом приоритета, ПКМ и повторное нажатие плитки отменяют инструмент. Сворачивание «Строительства» также отменяет placement без создания здания, сворачивает зелёную панель и возвращает синюю к компактному игровому дню.
12. Обычное окно только одно; fullscreen скрывает и восстанавливает UI; открытие не включает паузу.
13. Лента идёт сверху вниз от новых к старым; журнал/unread остаются отдельным будущим этапом с настоящим источником, без фиктивных событий, состояния прочтения и кнопок. Личный diary остаётся отдельной функцией и фильтруется по дню без изменения retention.
14. Time UI использует GameTime; F10 остаётся developer interface без видимой кнопки.
15. UI-клики не создают world actions; scroll таблиц/окон не масштабирует камеру, поиск не запускает hotkeys. Одно Esc обрабатывает только первый применимый уровень: верхний диалог, обычное окно, инструмент. MMB, wheel и остальные camera/tool controls сохранены.
16. Во вкладке «Инфо» развёрнутой карточки здания видима неактивная «Демонтировать». Нажатие ничего не выполняет, подтверждение не открывается, частичные API не вызываются, готовые здания не удаляются и материалы не возвращаются.
17. Не введены новые formulas, limits, bonuses, jobs, resource ledgers, assignment registries или второй selection.

В этой задаче проверяются полнота спецификации, согласованность с исходными требованиями, ссылки на существующие источники и отсутствие изменений за пределами документации. Q1–Q9 согласованы. Архитектурный аудит и план внедрения, затем реализация и её Godot/rendered QA выполняются следующими отдельными задачами; этот коммит не начинает их.
