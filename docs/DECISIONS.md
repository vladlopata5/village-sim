# Village Sim — Technical Decisions

## 2026-10-04

### Engine

Используем Godot 4.x.

---

### Programming language

Используем GDScript.

Причины:
- простой синтаксис;
- похож на Python;
- подходит новичку;
- хорошо интегрирован в Godot.

---

### Project scale

Ориентировочный масштаб финальной игры:

- 30–50 жителей для обычного развитого поселения;
- около 100 жителей как примерный верхний предел.

Архитектуру необходимо проектировать с учётом такого масштаба.

Не требуется проектировать систему под тысячи жителей.

---

### Presentation

Первый прототип использует 2D-представление для скорости и простоты разработки.

Финальный формат пока не определён.

Возможные варианты:
- 2D;
- изометрия / 2.5D;
- полноценное 3D.

Основные системы симуляции не должны зависеть от 2D-рендеринга.

Будущий переход к 2.5D или 3D должен быть возможен без переписывания основной игровой логики.

---

### Separation of simulation and presentation

Основная симуляция должна быть отделена от визуального представления.

Примеры:

- данные жителя не должны зависеть от Sprite2D;
- принятие решений жителем не должно зависеть от анимации;
- игровая логика здания должна быть отделена от его графического представления;
- игровое время не должно зависеть от частоты кадров;
- экономика не должна зависеть от типа камеры;
- события должны существовать как игровые данные, а не только как текстовые сообщения.

Временная графика и placeholder-объекты допустимы.

---

### Development approach

Разработка ведётся небольшими шагами.

Каждая задача должна быть:
- небольшой;
- понятной;
- проверяемой.

Не реализовывать системы, которые не нужны для текущей стадии ROADMAP.

Не пытаться заранее строить архитектуру всей будущей игры.

---

### Architecture

Предпочитать простую композицию сложным иерархиям наследования.

Не использовать ECS и другие сложные архитектурные подходы на раннем этапе без реальной необходимости.

Код должен оставаться понятным владельцу проекта.

---

### Inhabitant data

Данные жителя должны быть отделены от его визуального объекта.

Пример разделения:

PersonData:
- имя;
- возраст;
- характер;
- навыки;
- потребности;
- отношения;
- история.

Visual representation:
- позиция;
- спрайт или модель;
- анимация;
- визуальные эффекты.

Такое разделение должно позволить позже заменить 2D-представление на 3D без переписывания данных жителя.

---

### Inhabitant AI

Жители автономны.

Первая версия ИИ использует простую систему приоритетов.

Решения могут зависеть от:
- времени суток;
- потребностей;
- назначенной работы;
- поручений игрока;
- характера;
- текущего состояния.

Не использовать машинное обучение.

Не использовать сложные AI-системы, пока простая система приоритетов справляется с задачей.

---

### Time system

В игре существует собственное симулируемое время.

Начальный распорядок:

- 06:00–07:00 — утро;
- 07:00–17:00 — рабочий день;
- 17:00–23:00 — вечер;
- 23:00–06:00 — ночь.

Точное расписание может измениться после тестирования.

Игровое время не должно быть связано напрямую с FPS.

---

### Simulation updates

Не пересчитывать полный ИИ каждого жителя каждый кадр.

Решения должны пересчитываться:
- через разумные интервалы;
- после завершения действия;
- при изменении важных условий;
- при наступлении новой фазы суток.

Это важно для производительности и предсказуемости симуляции.

---

### UI philosophy

Не показывать игроку все внутренние числовые значения.

Часть информации должна передаваться через:
- текстовые описания;
- поведение жителей;
- разговоры;
- дневную летопись;
- визуальные состояния.

При этом важная управленческая информация должна оставаться понятной.

Игрок не должен быть вынужден вручную разговаривать с каждым жителем только для того, чтобы заметить критическую проблему.

---

### Conversations

Разговоры предназначены для получения более личной информации.

Они не заменяют основной интерфейс управления.

Через разговор можно узнавать:
- желания;
- сомнения;
- отношения;
- мнение о работе;
- семейные проблемы;
- скрытые интересы.

Базовые проблемы вроде болезни, голода или отсутствия жилья должны быть видимы без разговора.

---

### Daily chronicle

Игровые события должны сохраняться как данные.

У события может быть уровень важности.

Пример:
- normal;
- interesting;
- important;
- critical.

Дневная летопись выбирает наиболее значимые события и показывает их игроку в конце дня.

Критические события могут сообщаться сразу.

---

### Version control

Используем Git.

Основная ветка:

main

Коммиты делать после значимых работающих этапов.

Не объединять много несвязанных изменений в один большой коммит.

---

### Documentation

Основные документы проекта:

- AGENTS.md
- docs/GAME_DESIGN.md
- docs/ROADMAP.md
- docs/DECISIONS.md

GAME_DESIGN описывает игру.

ROADMAP описывает порядок разработки.

Если принято важное техническое решение, которое повлияет на дальнейшую разработку, его необходимо добавить в DECISIONS.md.

### Phase 1 — time and temporary presentation

- Часы — отдельный Node, без зависимостей от 2D; обмен через сигналы минут и фаз.
- Начало: 06:00; x1 = 1 игровая минута за реальную секунду. Это настраиваемый темп прототипа.
- Монотонные Time.get_ticks_usec() учитывают прошедшее время независимо от FPS; дробные минуты сохраняются.
- Пауза: SceneTree.paused. Камера и интерфейс работают всегда; часы исключают время паузы. Engine.time_scale не меняется.
- Фазы: утро 06–07, день 07–17, вечер 17–23, ночь 23–06. В Phase 1 скорость выбирает игрок; автоматическое ускорение ночи пока не реализуется.
- Поле и Camera2D — временное заменяемое представление.

---

### Phase 2 — resident data and replaceable view

- ResidentData — RefCounted с четырьмя полями: ID, имя, возраст, профессия. Данные не зависят от дерева сцены или 2D/3D.
- Main хранит одного тестового жителя независимо от визуального узла. Уникальный ID назначает создающий код; для единственного тестового жителя используется resident_001.
- ResidentView2D получает ссылку на существующие данные через setup(data), не хранит копии полей и не создаёт жителя. Представление можно удалить или заменить, сохранив данные.
- Позиция пока относится только к временному изображению; движение и другие части Phase 2 не реализованы.

---

### Phase 2 — selection and resident card

- Текущий выбор хранится в отдельном Node ResidentSelection как ссылка selected_resident на ResidentData. Выбор не зависит от типа визуального представления.
- ResidentView2D принимает необработанный левый клик по силуэту и передаёт данные сигналом selection_requested. Main связывает сигнал с выбором; пустое поле снимает выбор после обработки UI и жителя.
- ResidentCard читает выбранные данные через ResidentSelection. Карточка хранит только ссылку на узел выбора и UI-элементы; собственных полей жителя нет. Открытая карточка обновляется из исходных данных.
- Закрытие карточки снимает выбор. Клики по UI не проходят на поле. Выбор и карточка доступны на паузе.
- ResidentData остаётся без зависимостей от UI, выбора и визуальных узлов. Движение и другие системы этим шагом не добавлены.

---

### Phase 2 — basic personality traits

- TraitData — отдельный Resource с id (StringName) и display_name. Стабильные ID не зависят от отображаемого названия; определения хранятся в assets/traits/*.tres.
- ResidentData.traits — собственный типизированный список ссылок на определения черт. Степану назначены hardworking, sociable, stubborn. Общие определения не содержат индивидуального состояния жителя.
- Карточка читает названия из выбранного ResidentData, без собственного списка черт или таблицы текстов. Все текущие черты известны.
- Будущие эффекты могут расширять определения; получение черт меняет список конкретного жителя; AI сможет читать ID. Будущая скрытость относится к конкретному жителю. Ни один из этих механизмов сейчас не реализован.

---

### Phase 2 — basic resident states

- hunger, fatigue, mood хранятся в ResidentData как целые числа. Setter ограничивает каждое значение диапазоном 0–100. Высокие голод/усталость означают большую выраженность; высокое настроение означает лучшее настроение.
- Степан начинает с hunger=20, fatigue=35, mood=65. Автоматических изменений, связи с чертами и игровых последствий нет.
- ResidentStateText содержит только преобразование чисел в описания, с границами 25, 50, 75. ResidentData не зависит от этого преобразования или UI.
- Карточка читает данные и по умолчанию отображает число и текст. show_state_numbers позволяет оставить только текст без изменения данных и без нового игрового управления.
- Будущие события/действия смогут менять числовые поля, а AI читать их. Эти системы пока не реализованы.

---

### Phase 2 — temporary manual movement

- Цель и текущая глобальная 2D-позиция относятся только к ResidentView2D. ResidentData не изменён и не хранит пространственные данные визуальной сцены.
- move_to(world_target) — отдельный метод команды. Main выдаёт команду выбранному жителю по правому клику внутри поля после обработки UI. Координаты учитывают Camera2D.
- Скорость: 120 пикселей/сек на x1, умноженная на GameTime.speed_multiplier, передаваемый сигналом speed_changed. Движение учитывает delta и использует move_toward для остановки без перелёта.
- На паузе ввод доступен, но движение не выполняется и время движения не накапливается. Цель сохраняется или может заменяться новой командой. Снятие выбора не отменяет уже выданную команду.
- Обработка мыши отделена от метода перемещения; будущий источник решений сможет заменить ручной ввод. При переходе к 3D заменяется визуальное перемещение, а ResidentData и выбор сохраняются. Общей пространственной симуляции пока нет.
- AI, поиск пути, препятствия, работа, связь с чертами и изменение потребностей не реализованы.

---

### Phase 2 — one fixed night-home reaction

- Актуальный домашний объект — обычный BUILT BuildingInstance HOME home_stepan
  в (-300, -120), с общим BuildingView2D и housing связью.
- NightHomeController — отдельный Node, подписанный на GameTime.phase_changed. Он выдаёт movement_requested(home_position) при наступлении ночи и при настройке в уже ночной фазе.
- Main соединяет командный сигнал с ResidentView2D.move_to. Ручные правые клики также проходят через NightHomeController.request_manual_move: ночью они отклоняются, вне ночи разрешены.
- Приоритет дома сохраняется до 06:00, включая полночь, паузу и время после прибытия. Утром новой автоматической команды нет; ручное управление снова доступно.
- Контроллер не зависит от UI; ResidentData и механика движения не изменены. Сон, изменения состояний, система задач, работа и AI выбора действий не добавлены.

---

### Phase 2 — current intent mechanism

- ResidentIntent — RefCounted с типами NONE и MOVE_TO; MOVE_TO содержит reason_id, target_position и priority. Координаты относятся к временному 2D-прототипу и не попадают в ResidentData.
- ResidentIntentController хранит current_intent и передаёт его исполнителю сигналом intent_changed. NightHomeController теперь создаёт намерения вместо прямых команд изображению.
- Домашнее намерение: night_home, приоритет 100; ручное: manual_move, приоритет 10. Более высокий приоритет вытесняет текущий. Более низкий или равный от другого источника отклоняется. Равный приоритет с тем же ID обновляет цель, сохраняя повторные ручные клики.
- ResidentView2D сообщает о прибытии сигналом intent_completed с конкретным объектом намерения. Контроллер очищает до NONE только совпадающее текущее намерение; устаревшие уведомления игнорируются.
- Ночной запрет ручных команд остаётся в источнике решений, включая время после прибытия. В 06:00 незавершённый домашний путь получает приоритет 0 без отмены движения, позволяя ручной команде снова заменить его.
- При очередном этапе старое описание прямых сигналов движения заменено механизмом намерений. ResidentData, UI, состояния и черты не изменены; очередей задач и полноценного AI нет.


## Debug-перемотка и начало утра

Временные Shift+1/Shift+2/Shift+3 проходят через общий поминутный механизм GameTime, включая сигналы всех пересечённых фаз. Явная перемотка разрешена на паузе и не умножается на скорость. Shift+3 выбирает строго следующую границу фазы и обнуляет дробную минуту. Перемещение за пропущенное время не рассчитывается.

В 06:00 NightHomeController снимает блокировку ручных команд и через clear_reason(night_home) отменяет оставшееся ночное намерение. Это заменяет прежнее снижение приоритета до 0: незавершённое движение останавливается сигналом NONE, утренней автоматической цели нет.


## Phase 2 завершён; Phase 3 — текущее занятие

Phase 2 завершён. ResidentIntent и NightHomeController — ранняя основа Phase 3. Shift+1/Shift+2/Shift+3 остаются debug-инструментами разработки.

ResidentActivity.Type определяет IDLE, MOVING, SLEEPING. Одно текущее значение хранится в ResidentData.activity без координат и ссылок на сцены. Intent описывает цель, Activity — текущее занятие. ResidentIntentController отмечает MOVING при принятии MOVE_TO и IDLE при завершении/отмене. Только подтверждённое завершение испускает intent_completed; отмена и устаревшее уведомление не означают прибытия.

NightHomeController переводит жителя в SLEEPING после подтверждённого прибытия по night_home ночью. В 06:00 незавершённое ночное намерение отменяется, а спящий становится IDLE. Сон пока не изменяет состояния. UI лишь читает activity и переводит enum в подпись. Отдельные контроллеры будущих занятий не создаются.


## Phase 3 — WorldLocation и домашнее место

WorldLocation — RefCounted с id и display_name, без пространственных данных.
Актуальная реализация: ResidentData.home_location_id ссылается на обычный
BuildingInstance HOME. WorldLocations2D сопоставляет этот building ID с данными
места/BuildingView2D и возвращает актуальную позицию или null. Schedule использует
этот mapping, либо position экземпляра; отдельного домашнего объекта нет.

Для 3D сохраняется ID и WorldLocation; заменяются механизм положения и пространственная часть намерения/исполнителя. Уже выданный MOVE_TO содержит снимок позиции на момент команды. Строительство, универсальная система сущностей и новые занятия не добавляются.


## Phase 3 — единый ResidentScheduleController

NightHomeController заменён ResidentScheduleController и удалён: один источник расписания слушает фазы и завершение намерений. 07:00 создаёт day_work (50) к work_location_id, прибытие означает WORKING; 17:00 отменяет незавершённый рабочий путь/заканчивает работу до IDLE. 23:00 создаёт night_home (100), прибытие означает SLEEPING; 06:00 отменяет путь/заканчивает сон до IDLE. Manual_move (10) допускается только утром и вечером, включая паузу. Днём и ночью запрет сохраняется после прибытия.

На Phase 3 WorldLocation/work_location_id представляли рабочее место без производства.
Теперь work_location_id ссылается на обычное рабочее здание; представление —
BuildingView2D, позиционный mapping — WorldLocations2D. Прежние разделы фиксируют
историю реализации; актуальные production/logistics/work правила описаны в Phase 4.


## Phase 4 — только голод

Phase 3 считается завершённым. ResidentHunger слушает GameTime.minute_changed и изменяет исходный ResidentData.hunger. Бодрствование (IDLE/MOVING/WORKING): +1 за 15 игровых минут; SLEEPING: +1 за 60 минут. Целый накопитель долей (60 долей = 1 пункт, +4/+1 за минуту) сохраняет остаток при смене занятия без ошибок округления. При 100 остаток сбрасывается; setter ResidentData ограничивает диапазон 0–100.

Нет _process для потребности, UI только читает данные. Обычная пауза не испускает минуты. x1/x2/x4 ускоряют игровое время и поэтому рост в реальных секундах. Shift+1/Shift+2/Shift+3 на паузе явно продвигают время и тоже увеличивают голод; минутный сигнал обрабатывает прошедшую минуту перед переключением фазы. Shift+4 — временное +25 выбранному жителю, работает на паузе, повтор клавиши игнорируется. Нет выбора/закрыта карточка — нет действия.

Голод, включая 100, не влияет на расписание, намерения или занятия. Усталость и настроение не меняются. Еда, восстановление и последствия не реализованы.


## Phase 4 — данные первого здания

BuildingData (RefCounted) хранит только id/display_name/type; BuildingType.Type пока содержит FOOD. Main хранит одно тестовое здание communal_kitchen_01 / «Общая кухня». Отдельный WorldLocation создаётся с тем же ID: совпадение ID связывает два различных объекта данных. WorldLocation не содержит BuildingData, тип или координаты.

BuildingView2D получает исходный BuildingData, рисует временный прямоугольник и показывает название. Существующий WorldLocations2D регистрирует WorldLocation на этом Node2D и возвращает актуальную позицию. Нет второго реестра координат или BuildingManager. Удаление/замена изображения сохраняет данные здания и ID места. Будущий 3D-вариант заменит только представление и пространственное сопоставление.

Кухня пока не взаимодействует с голодом или расписанием; производство, ресурсы, запасы, стоимость, строительство, EATING и новые намерения отсутствуют.


## Phase 4 — реакция на голод и еда

ResidentNeedsController обрабатывает только голод через hunger_changed, minute_changed и phase_changed. Main передаёт простой список BuildingData; контроллер выбирает FOOD и разрешает WorldLocation/позицию через существующий WorldLocations2D. При голоде >=70 вне сна/ночи создаётся MOVE_TO eat (75), выше работы (50) и ручного ввода (10), ниже дома (100). Прибытие по конкретному принятому намерению начинает EATING и 30 игровых минут еды. Повторы маршрута не выдаются; ночное вытеснение отменяет таймер без эффекта еды.

EATING сохраняет приоритет после очищения MOVE_TO: расписание не выдаёт рабочую цель и ручные команды не принимаются до завершения, но ночь прерывает. В конце hunger уменьшается на 60 (clamp ResidentData), activity=IDLE, расписание resume_current_phase() возвращает дневной рабочий маршрут или оставляет IDLE утром/вечером. Рост голода во время EATING остаётся обычным. Shift+6 — debug установить 75 выбранному жителю. Еда бесконечна, без ресурсов/запасов; новые типы намерений не нужны. Усталость и настроение не меняются.


## Phase 4 — общий запас FOOD

ResourceType.Type.FOOD и один SettlementStorage (RefCounted) в Main хранят общий запас поселения по типу; старт 10. try_consume() проверяет и списывает атомарно, без отрицательного остатка. changed обновляет UI «Еда: X»; Shift+8 добавляет 5.

В конце еды ResidentNeedsController списывает 1 FOOD, только успех уменьшает hunger на 60. При пустом запасе на старте попытка длится 5 игровых минут; при опустевшем запасе в конце обычной еды также нет снижения. Неудача возвращает IDLE и emits developer_message/печатает сообщение. Повторные попытки блокируются до положительного пополнения, без цикла EATING. Пополнение во время короткой попытки начинает полный таймер 30 минут. Ночь отменяет попытку без списания. Ресурсы в начале не резервируются; кухня не хранит свой инвентарь.


## Изменение дизайна: ресурсы только в конкретных местах

Ресурсы НЕ являются глобальными числами поселения: они находятся в локальном контейнере владельца/места или физически в мире. В будущем конкретные жители переносят их между производством, складами и зданиями. Сводный счётчик может быть статистикой, но не источником списания.

SettlementStorage и его тест удалены; предыдущий раздел про общий запас — отменённое решение. ResourceType сохранён. ResourceContainer(owner_id) предоставляет get_amount/add/has_resource/try_take. BuildingData.resources — собственный контейнер каждого здания; Общая кухня стартует с 3 FOOD, другие запасы не создаются. Main больше не владеет глобальным запасом.

ResidentNeedsController удерживает выбранный BuildingData и завершает еду только через его resources; пополнение другого контейнера не оплачивает и не разблокирует её. UI показывает «Еда в кухне: X»; Shift+8 добавляет 1 только кухне. Неудача и возврат к расписанию сохранены. Будущая переноска потребует явного изъятия у источника и доставки в назначение, без автоматической пересылки сейчас. BuildingData/ResourceContainer остаются данными, без Node2D или UI.


## Phase 4 — непрерываемые намерения и pending

Прежнее решение о ночной отмене EATING заменено: путь к кухне прерываем, начатая еда непрерываема. ResidentIntent.interruptible и один pending_intent в ResidentIntentController обеспечивают общий механизм без очереди. Более высокий приоритет запускается сразу при прерываемом current, иначе ждёт; pending сохраняет наиболее приоритетный запрос. После подтверждённого завершения current pending активируется автоматически.

Прибытие выделено в intent_arrived: обычный MOVE_TO завершается сразу, но ResidentNeedsController сохраняет eat и блокирует его прерывание на время еды. По окончании проверяется только локальный FOOD кухни, затем завершается намерение. Ночь ждёт завершения еды/неудачной попытки; 06:00 удаляет устаревшее night_home также из pending. Приоритеты 10/50/75/100 сохранены. ResidentData не получает координат или визуальных ссылок, UI не управляет намерениями.


## Phase 4 — подготовка физической логистики

Логистику выполняют назначенные носильщики. До переноски резервируются ресурсы у источника (reserved_out) и свободное место у назначения (reserved_in). Смена распорядка не должна заставлять жителя бросать уже взятый груз: будущий перенос должен завершать безопасную доставку через механизм непрерываемого действия/pending. Сейчас переноска, HaulJob, поиск дефицита и инвентарь не реализованы.

Тестовый Склад: warehouse_01, BuildingType.STORAGE, отдельные BuildingData, WorldLocation и BuildingView2D. Его локальный FOOD=10, вместимость FOOD=20. Кухня стартует FOOD=0, вместимость FOOD=5. Существующий WorldLocations2D разрешает позиции обоих мест. UI показывает каждый запас отдельно. Степану назначен ResidentProfession.Type.PORTER («Носильщик»); второй тип NONE («Без профессии»). Профессия пока не меняет поведение или расписание.

ResourceContainer хранит фактические количества, capacity_per_resource и отдельные reserved_out/reserved_in по типу ресурса. Доступно для изъятия: amount-reserved_out; свободно физически: capacity-amount; доступно для доставки: capacity-amount-reserved_in. Ненастроенная вместимость равна 0; set_capacity не позволяет уменьшить её ниже amount+reserved_in.

reserve_out/reserve_in проверяют весь запрос и изменяют только резерв; release_out/release_in освобождают его. take_reserved/add_reserved изменяют фактический запас и одновременно уменьшают соответствующий резерв. Обычные try_take/add также учитывают резервы. Нулевые, отрицательные и чрезмерные запросы отвергаются целиком без частичного изменения. Резервирование ничего не перемещает. Счётчики пока агрегированы, без ID задач; будущий владелец задачи обязан хранить свои количества и освобождать собственные резервы при отмене.


## Phase 4 — одна зарезервированная логистическая задача

HaulJob — отдельный RefCounted: стабильный ID, source_location_id, destination_location_id, resource_type, amount, assigned_resident_id и state. Состояния только RESERVED, ASSIGNED, CANCELLED, COMPLETED; последнее зарезервировано для будущего реального завершения доставки, сейчас автоматически не наступает. Задача не хранит координат и не перемещает ресурс.

LogisticsController обслуживает только warehouse_01 → communal_kitchen_01, FOOD, по 1 единице, и хранит одну current_job без очереди. Целевой запас кухни 3: проверяется amount+reserved_in. Создание требует доступного FOOD у источника и доступной вместимости у назначения; активная RESERVED/ASSIGNED задача блокирует дубликат. Сначала reserve_out, затем reserve_in; отказ второго шага освобождает только первую бронь этой попытки. Данные HaulJob создаются только после обеих успешных броней. cancel_job подтверждает тот же активный объект, освобождает обе его брони и отмечает CANCELLED; повторная/устаревшая отмена ничего не меняет.

Задача становится ASSIGNED, если Степан PORTER и его work_location_id=warehouse_01; иначе остаётся RESERVED до следующего пересчёта. При назначении нет ResidentIntent, движения или изъятия/добавления FOOD. Старый WorkPoint/work_stepan удалён: существующее расписание в 07:00 ведёт Степана на Склад и после прибытия ставит WORKING.

Пересчёт выполняется один раз при запуске и вручную через временный Shift+9 (также на паузе, без повторов удержанной клавиши); автоматического пересчёта запасов пока нет. UI читает фактические количества, вместимость, обе брони и назначение. Старт: склад 10/20, reserved_out=1; кухня 0/5, reserved_in=1; Степан назначен доставить 1 FOOD. Shift+9 не увеличивает брони и не переносит еду. Обычные add/try_take защищают обещанные количества/место; отдельные типы ресурсов имеют отдельные вместимости. Груз и исполнитель доставки появятся следующим шагом.

Проверки: test_logistics.gd подтверждает обе брони, откат второй неудачи, сохранность чужих резервов, отсутствие дубликатов, целевой запас, отсутствие доступного FOOD/места, позднее назначение, отмену, реальные Shift+9 и отсутствие движения/списания при назначении. test_resident_schedule.gd проверяет весь цикл расписания уже с рабочим местом на складе.


## Phase 4 — физическая доставка одной FOOD

Этот шаг заменяет прежнее ограничение «задача только назначается». LogisticsController теперь связывается с GameTime, WorldLocations2D, ResidentIntentController и расписанием. HaulJob проходит RESERVED → ASSIGNED → GOING_TO_SOURCE → CARRYING → GOING_TO_DESTINATION → COMPLETED. CARRYING — короткий этап непосредственно после подбора; следующие кадры показывают GOING_TO_DESTINATION и груз у жителя. В контроллере остаётся только одна текущая задача; завершённая заменяется следующей, если кухня ещё ниже target stock=3 и есть доступная FOOD.

ResidentData.inventory содержит отдельный ResidentInventory (RefCounted) с resource_type и amount, без координат. Он принимает только одну FOOD в пустой слот. ResidentActivity.HAULING («Несёт груз») означает движение с этим грузом. ResidentView2D читает инвентарь и показывает маленькую подпись «■ FOOD»; это не хранилище ресурса.

Дневной маршрут haul_source имеет приоритет 80 (выше работы 50, еды 75 и ручных команд 10, ниже night_home=100), interruptible=true. При подтверждённом прибытии вызывается take_reserved(FOOD,1): количество/исходящая бронь склада уменьшаются, FOOD оказывается в инвентаре. Грузовой маршрут haul_destination получает interruptible=false. continue_intent() переводит одно действие на следующий маршрут с сохранением pending, не завершает всю доставку при подборе.

По прибытии к кухне груз удаляется из инвентаря, add_reserved(FOOD,1) увеличивает её запас и уменьшает входящую бронь, задача становится COMPLETED. Только затем намерение завершается и pending (в частности night_home) активируется. При неудаче добавления груз возвращается в инвентарь; он не теряется. Повторные/устаревшие сигналы прибытия не подбирают и не доставляют FOOD второй раз.

В 17:00 уже начатые оба маршрута продолжаются. После вечернего завершения житель IDLE, новые доставки до утра не запускаются. В 23:00 путь к источнику прерывается: CANCELLED, освобождаются обе брони, FOOD остаётся в складе, Степан идёт домой. На следующий рабочий день создаётся новая задача. С грузом отмена запрещена: night_home остаётся pending, доставка завершается перед уходом домой. Утром существующая очистка устаревшего night_home также действует при длинной debug-перемотке.

Потребность не прерывает уже взятый груз; после доставки контроллер потребностей снова оценивает голод, при необходимости ест из локальной кухни и потом продолжает логистику. На обычной паузе движение стоит; скорости x1/x2/x4 используют прежнюю механику. Shift+9 пересчитывает логистику и в рабочий период может назначить маршрут; Shift+1/Shift+2/Shift+3 меняют часы, но не симулируют пройденный путь.

Проверка: F5 → Shift+3 до 07:00 → дождаться трёх рейсов. Без еды и debug-добавлений склад 7, кухня 3, инвентарь 0, reserved_out/reserved_in=0, Степан возвращается к WORKING. Значок появляется только между подбором и доставкой. Через Shift+3 перейти в вечер/ночь до или после подбора, проверить описанные различия. test_physical_haul.gd проверяет сохранение общей FOOD на каждом этапе, target stock=3, паузу/скорости, повторные прибытия, мгновенный подбор, ручной ввод, голод после доставки, вечер, обе ночные ветки и новый рабочий день. Прежние проверки подсистем отключают исполнение логистики через unbind_execution(), чтобы отдельно проверять свои правила; интеграционный тест выполняет настоящий общий цикл.


## Phase 4 — forced interrupt, критический голод и FOOD на земле

Обычный submit() сохраняет правила приоритетов, interruptible и одного pending. Отдельный force_set_intent() игнорирует приоритет/interruptible, очищает pending и испускает forced_interrupt перед включением нового current. Обработчик текущей системы очищает задачу и её ресурсы; это отмена, не успешное завершение. Принудительное намерение защищено от обычных submit/clear_reason до завершения; новое forced может заменить его. После завершения снова действуют обычные правила.

ResidentNeedsController: hunger=100 немедленно прерывает текущую деятельность ради еды, также ночью или во сне. При уже начатой еде она продолжается, получая forced-защиту без сброса таймера. Если кухни/позиции нет — forced NONE останавливает действие. Чтобы не повторять пустую попытку каждую минуту, critical attempt запоминается до ухода голода ниже 100; прежнее ожидание пополнения кухни сохраняется. После неудачной попытки работа может продолжиться для доставки еды; пополнение разрешает следующую попытку. Усталость и настроение не меняются.

76–99 не прерывает текущую работу/переноску. Проверка prepare_for_work и intent_completed даёт попытке поесть приоритет перед следующим рабочим действием. Если еда отсутствует, короткая попытка завершается по прежним правилам; новые рабочие действия снова допустимы. 70–75 сохраняет прежнюю реакцию. Shift+7 — временная установка голода выбранного жителя в 100; Shift+6 по-прежнему 75. Работает на паузе, без выбора и при удержании не повторяет действие.

Forced до подбора: HaulJob=CANCELLED, обе брони освобождаются, FOOD остаётся на складе. Forced после подбора: HaulJob=CANCELLED, освобождается только reserved_in назначения, исходящий резерв уже израсходован. Инвентарь очищается, cargo_dropped передаёт FOOD в отдельный GroundResource в фактической позиции Степана; запасы склада и кухни не увеличиваются. Повторное/устаревшее прибытие не доставляет брошенную еду. Обычная ночь по-прежнему ждёт завершения переноса с грузом.

GroundResource — отдельные RefCounted-данные: resource_type, amount, world_position (Vector2 временного мира), created_at, lifetime=4320 игровых минут, age_minutes(). Координата есть у объекта мира, не у ResidentData/инвентаря. Main связывает отдельные GroundResources и GroundResourceView2D: первый хранит активные объекты и удаляет их по GameTime.minute_changed; второй только рисует квадрат/подпись FOOD. Данные не зависят от картинки; контейнеры не считают ресурс на земле своим запасом. Нет подбора или возврата на склад.

Срок — ровно три игровых дня после создания, а не календарная граница третьего дня. Обычная пауза не старит объект, x1/x2/x4 ускоряют игровые минуты; Shift+1/Shift+2/Shift+3 явно продвигают возраст и на паузе. При истечении активные данные удаляются и изображение освобождается.

Проверка: F5 → Shift+3 до 07:00 → выбрать Степана → Shift+7 до/после подбора. До подбора еда остаётся на складе; после — появляется квадрат FOOD на месте остановки, инвентарь пуст, бронь кухни 0. Восстановить еду кухне через Shift+8 для проверки питания. Для исчезновения использовать Shift+2 двенадцать раз (72 игровых часа) либо обычное время. test_emergency.gd проверяет обычный pending, forced меньшего числового приоритета, обе стадии отмены, сохранность чужого исходящего резерва, место/изображение FOOD, отсутствие дубликатов, паузу/скорости, 4319/4320 минут и сильный голод перед новой задачей. Запускаются все tests/test_*.gd.


## Phase 4 — фабрика и коллекция самостоятельных жителей

Убран единственный житель как предположение Main. ResidentFactory — единственная точка создания стартовых/генерируемых ResidentData; ResidentGenerator поверх неё имеет локальный seeded RNG и namespace/счётчик ID. Одинаковые seed/namespace воспроизводят последовательность; поселение использует один генератор для namespace и проверяет уникальность своей коллекции. Случайны только ID, имя, возраст, 2–3 врождённые черты и стартовые состояния. Профессия, дом и рабочее место назначаются поселением отдельно. Пол пока отсутствует.

ResidentRuntime — простой комплект контроллеров одного жителя, без универсальной системы сущностей/профессий. У каждого свои intent/pending, голод и его дробный накопитель, таймер питания, расписание и инвентарь. ResidentData остаётся вне сцены, без координат/ссылок на представление. Общими остаются часы, реестр мест, кухня и её локальный запас. Дом задаётся ссылкой по ID и не ограничен одним владельцем.

Main направляет ручную команду в runtime выбранных данных, имя исполнителя логистики получает по assigned_resident_id, позицию брошенного груза — из представления конкретного носильщика через связанный callback. Ссылки на resident_001/Степана остались только в стартовом сценарии и тестовых ожиданиях; ResidentNeedsController не знает их. Степан пока единственный PORTER склада, автоматического выбора исполнителя между носильщиками нет. Существующие приоритеты, forced interrupt, резервы и физическая доставка сохранены.

Для старых тестов одной подсистемы введён явный isolate_first; это тестовая изоляция, а не ограничение игры. Отдельная интеграционная проверка использует реальную коллекцию из четырёх, общую кухню и независимые контроллеры.


## 2026-10-05 — общий Need и точки принятия решений

Этот шаг заменяет прежние правила фиксированного порога 70/76, неизменной усталости, попытки есть без брони и списания/снижения голода только в конце. Предыдущие разделы описывают историю реализации.

- NeedType сейчас только HUNGER/FATIGUE. ResidentData.needs хранит отдельные Need(value 0–100, base_weight=100); hunger/fatigue — доступ к этим же значениям для карточки, фабрики и debug, без дублирующих чисел. get_effective_weight пока возвращает base_weight. Формула need_priority=value*effective_weight, общий threshold=1000.
- NeedDynamics заменяет ResidentHunger и изменяет обе потребности по GameTime.minute_changed. Дробные накопители принадлежат конкретному жителю. Константы скоростей находятся только в need_dynamics.gd: голод +4/час бодрствуя, +1/час во сне, -2/минуту при оплаченной еде; усталость IDLE/EATING +1/час, MOVING +2, WORKING +4, HAULING +5, RESTING -10, SLEEPING -30. UI ничего не считает. Модификаторов черт и изменений mood нет.
- DecisionController — отдельный компонент каждого ResidentRuntime. Нет кадрового цикла решений: обычное сравнение вызывается по завершению действия, его невозможности, пробуждению/фазе дня, появлению доступного способа для свободного жителя. Старт/безделье и временная работа на месте — десятиминутные отрезки; их завершение создаёт decision point. Изменение обычного значения само по себе не перепланирует занятого жителя; сигналы значений проверяют только critical.
- WORK_PRIORITY=7000: при наличии новой рабочей задачи потребности <=7000 уступают работе; >7000 сначала пробуют свой доступный способ. На равенстве выигрывает работа; равенство двух потребностей решается в пользу голода. LogisticsController.has_work сообщает единственному назначенному носильщику, есть ли реальная доставка. Если задач нет, потребность может победить и ниже 7000; иначе IDLE на 10 минут. Временные исполнительные приоритеты согласованы: manual=10, work=7000, haul=8000, night_home=10000. Они не заменяют сравнение потребностей на границе действий.
- force_set_intent(intent, critical_priority) имеет отдельный уровень защиты: hunger=100 — 200, fatigue=100 — 100, старый общий forced-вызов по умолчанию 1. Более низкий critical не заменяет более высокий, обычный submit не заменяет forced. Критическая еда защищена до конца тридцатиминутного действия, несмотря на падение значения голода. После неё fatigue=100 снова рассматривается и запускает сон на месте. Критический сон завершается при fatigue<=20; утренний режим не отменяет незавершённый сон от истощения. Новый более высокий critical может его прервать.
- RESTING добавлен в Activity и карточку. Для неподвижного действия используется существующий Intent.Type.NONE с непустым reason_id (rest/critical_sleep), а пустой NONE означает отсутствие действия; новых типов маршрута не добавлено. has_current_action отличает эти случаи. Позиции не появились в ResidentData или Need.
- Потребность и способ её удовлетворения разделены: DecisionController выбирает Need, ResidentNeedsController пробует конкретную кухню/отдых. Только после выбора кухни reserve_out(FOOD,1) обещает конкретному контроллеру одну единицу до пути. Агрегированные резервы одного ResourceContainer защищают и логистику, и еду; владелец действия хранит свою бронь и освобождает только её. Отмена, пропавший/сдвинутый маркер или невозможность действия освобождают бронь и вызывают новый выбор. Нельзя компенсировать отсутствие еды кухне запасом склада.
- take_reserved расходует FOOD при начале EATING, до постепенного эффекта. Так отменённая критическим событием оплаченная еда не возвращает ресурс и не даёт бесплатный полный эффект. Приём пищи продолжается 30 игровых минут, по -2 голода в минуту, без скачка в конце. Изменение голода по дороге использует прежнюю скорость бодрствования. Обычная ночь по-прежнему ждёт окончания непрерываемой еды; critical hunger/fatigue используют уровни forced. Critical-переноска по-прежнему отменяет HaulJob с GroundResource после подбора и корректными бронями.
- Резервирование, списание и forced-события могут вызывать сигналы синхронно. Начало еды защищено от повторного списания; после сигнала проверяется, осталось ли действие текущим. Critical, возникшее внутри обычного выбора, обрабатывается после защищённого участка, а не теряется. Никакой универсальной job/priority framework не добавлено.


## 2026-10-05 — SOCIAL/LEISURE, weighted random и разговорные группы

- NeedType дополнен SOCIAL (base_weight=70) и LEISURE (50), отдельные Need принадлежат ResidentData. DecisionController сравнивает четыре потребности, с прежними порогами 1000/7000. При равных приоритетах порядок категорий стабилен, голод первый.
- Конкретные социальные/досуговые действия вынесены в ResidentSocialController каждого ResidentRuntime. Он не выбирает самую важную потребность. SocialWorld хранит текущие группы и доступность участников; позиции получает через position_provider. Main задаёт временный 2D-адаптер. Для другого представления меняется адаптер, а ResidentData и ConversationGroup не получают визуальных координат/ссылок.
- Варианты общения — отдельные записи target_id/group_id/option_weight. Одна группа даёт один вариант, независимо от числа участников. Вес = 500/(1+distance*0.5/500): всегда положителен, расстояние снижает его. Модификаторы можно добавить при расчёте вариантов, не меняя Need. WeightedChoice.pick получает явно переданный RandomNumberGenerator; каждый контроллер имеет собственный RNG с seed от стабильного ID, тесты задают seed явно. Глобальная случайность не используется.
- ConversationGroup — данные с ID группы и списком ID жителей. Двое начинают группу; следующие присоединяются, предел размера не задан. Участники заканчивают действия независимо. При выходе до одного участника группа удаляется, оставшийся завершает своё действие и получает decision point; этот вызов отложен, чтобы не принимать решение внутри изменения состава группы.
- Путь к разговору прерываемый; начатый TALKING и RELAXING непрерываемы для обычных команд. Они длятся до потребности <=15 либо максимум 30 игровых минут. Ночь использует existing pending; critical использует existing forced. Замена intent удаляет участника из группы. Ручная команда не меняет уже выбранное социальное действие. Новые типы Intent или универсальная AI/job-система не создавались.
- Все изменения потребностей идут через GameTime.minute_changed с индивидуальными дробными остатками. SOCIAL/LEISURE rates определены в NeedDynamics, UI только читает четыре Need. При потере цели во время пути действие завершается с новым выбором; старое намерение не продолжает управлять движением.


## 2026-10-05 — носильщик сам запрашивает HaulJob

Этот шаг заменяет прежнее автоматическое назначение задачи конкретному Степану и запуск следующего рейса из LogisticsController.

- WORK_PRIORITY=7000 — приоритет категории работы при сравнении с Need.priority. HaulJob.priority — отдельная внутренняя срочность доставки, применяется только внутри claim_best_job. Для текущего маршрута при создании: max(0,3-actual_kitchen_food)*100. Более пустая кухня даёт большую срочность. Исполнительный приоритет маршрута haul=8000 защищает уже выбранное действие и не является HaulJob.priority.
- RESERVED теперь явно означает доступную незанятую задачу с уже существующими reserved_out/reserved_in и пустым assigned_resident_id. AVAILABLE не добавлен. LogisticsController хранит jobs, создаёт одну активную доставку по текущему маршруту; current_job остаётся указателем для существующего исполнителя и debug. При пересчёте нет назначения или движения.
- claim_best_job(resident_id) читает реестр жителей, проверяет PORTER и work_location_id=source_location_id, выбирает максимальный priority, на равенстве минимальный стабильный строковый ID. Выбор и перевод в ASSIGNED выполняются синхронно без сигналов/ожидания между ними. changed испускается после назначения; повторный/конкурирующий запрос не получает тот же объект. Claim не резервирует повторно, не перемещает FOOD и не создаёт задачу. У одного жителя не может быть двух активных назначений.
- DecisionController при дневной точке выбора сначала сравнивает доступную работу с четырьмя потребностями. Если работа выиграла, его work_request вызывает claim_best_job и существующий исполнитель начинает маршрут. Если задача уже недоступна, рассматриваются личные способы ниже 7000; при отсутствии подходящих способов — IDLE на 10 игровых минут. Работник без доступной задачи не идёт на склад ради фиктивного WORKING.
- ResidentScheduleController передаёт дневную точку выбора DecisionController вместо прямой команды носильщику. Main связывает конкретного носильщика с общим предложением задач; LogisticsController не вызывает сравнение потребностей и не заставляет свободного жителя начать доставку. Регистрация и claim принимают resident_id, без проверки имени или конкретного ID Степана. В игре по-прежнему один носильщик и один исполнитель; реестр/атомарное назначение подготовлены для будущих носильщиков, их одновременное исполнение сейчас не добавлялось.
- После COMPLETED логистика может подготовить следующий RESERVED offer, но прежнее намерение завершается через ResidentIntentController, создавая новый decision point. Только этот выбор может назначить следующий рейс. После CANCELLED исполнителю передаётся отложенная точка выбора, чтобы закончить forced/phase-cleanup до нового решения. Доступная неназначенная задача не отменяется из-за критического состояния свободного носильщика.
- Обычный рост потребности не прерывает начатый маршрут ни до, ни после подбора. После его завершения значение >7000 может победить перед следующим claim. Forced, груз на земле, ночной pending, вечернее завершение и смысл резервов сохранены.


## 2026-10-05 — производство в здании и динамическая логистическая срочность

Этот шаг заменяет предыдущие ограничения одной логистической трассы, target stock=3 и ступеней дефицита 300/200/100.

- Добавлены ResidentProfession.GATHERER и BuildingType.GATHERER_HUT. Фёдор назначен на gatherer_hut_01; профессия сама ничего не производит. BuildingData хранит production_progress в рабочих минутах и logistics_weight. Накопление переживает еду, отдых, замену/переназначение работников; ResidentData не хранит прогресс здания.
- GathererProduction — простой контроллер одного рецепта FOOD, подключённый к GameTime.minute_changed. Он суммирует жителей с GATHERER, подходящим work_location_id, Activity.WORKING и фактической позицией у здания (допуск 8 единиц). Позиции передаются отдельным Callable-адаптером Main, положение здания разрешает существующий WorldLocations2D. Симуляционные данные не получили координат/ссылок на визуальную сцену. Для каждого реально работающего — +1 рабочая минута за игровую минуту.

Полный контейнер или занятая входящими бронями вместимость запрещают новый прирост; обещание будущего вывоза не освобождает физическое место раньше take_reserved. Оставшийся progress сохраняется. Если ранее накопленных минут уже достаточно, их можно преобразовать при освобождённом месте и без нового вклада.

Изменение списка не может запретить ресурс, который уже фактически хранится или зарезервирован. Производственный контейнер не принимает посторонние типы. Универсального рецептурного framework нет.

Данные зданий разрешаются по source/destination ID задачи: резервирование, подбор, доставка, отмена и forced очистка обращаются к соответствующим локальным контейнерам, не к жёстко выбранному складу/кухне. PORTER работает на warehouse_01, но может забирать груз из хижины.

Это не инициирует движение. Срочность задачи может быть 0 при уже обещанном единственном ресурсе/последнем свободном месте: задача остаётся допустимой и выбирается, если более срочных нет.
- Kitchen target_stock удалён из логики. Свободная вместимость с учётом reserved_in — единственный количественный предел импорта; 3/5 не особая граница. Хижина экспортирует начиная с одной доступной FOOD. Claim не создаёт повторных броней. Завершение рейса сохраняет новый decision point, конкуренцию потребностей с WORK_PRIORITY и critical/forced/pending. Близость чисел HaulJob.priority и Need.priority не связывает их: сравнения между ними нет.

## Phase 4 — рабочие циклы, длительность разговоров и доступность FOOD

Текущий баланс в balance_config.gd: HUNGER/FATIGUE 100, SOCIAL 80,
LEISURE 75, WORK_PRIORITY 7000. SOCIAL=100 даёт 8000, LEISURE=100 — 7500:
они могут победить новую работу, но обычный рост не прерывает выбранное действие.
Хижина производит 1 FOOD за 30 фактических рабочих минут; кухня вмещает 20 FOOD.
Импорт продолжает рассчитываться от (amount + reserved_in) / capacity;
экспорт — от (amount - reserved_out) / capacity, без ступеней или target stock.

DecisionController начинает 60-минутный рабочий цикл только после прибытия
и перехода в WORKING. Завершение цикла создаёт обычную decision point:
новая работа снова сравнивается с доступными личными потребностями.
Forced/critical прерывание действует немедленно. Производственный progress
принадлежит BuildingData, сохраняется между циклами и при перерывах.
Минутный вклад производства учитывается до решения о следующем действии,
чтобы последняя отработанная минута не терялась на границе цикла.

SOCIAL инициирует поиск общения, но выбранный разговор имеет свою длительность.
Каждый участник отдельно отсчитывает минимум 15 и максимум 60 игровых минут.
После минимума переоценка выполняется раз в 5 минут: участник может выйти
ради доступного действия с более высоким текущим приоритетом либо с seeded
случайным шансом 20%. SOCIAL=0 само по себе не завершает разговор.
В 60 минут выход обязателен; critical/forced не ждёт минимума.
ConversationGroup сохраняется при 2+ участниках; при меньшем числе распадается,
оставшийся получает decision point. Числовое снижение SOCIAL/LEISURE сохраняется.

Первый слой event-driven availability применяется к FOOD. После неудачного
поиска ResidentNeedsController помечает способ недоступным: DecisionController
не повторяет этот поиск по таймеру, а выбирает другие действия.
ResourceContainer.availability_changed сообщает изменение amount - reserved_out,
в том числе при добавлении FOOD и освобождении исходящей брони. Новая доступная
порция снова разрешает поиск. Голодный IDLE-житель получает decision point;
занятый разговором, отдыхом, работой или переноской сохраняет своё действие
и учитывает новый вариант на следующей обычной границе. Даже ранее неудачный
critical hunger не превращает событие доступности в новый forced interrupt.
Само новое достижение critical HUNGER/FATIGUE по-прежнему прерывает действие.

Retry cooldown удалён. Редкий страховочный polling не добавлен: для текущих
фиксированных мест сигналы ресурсов и освобождения брони покрывают доступность еды.
Десятиминутный IDLE остаётся самостоятельным fallback-действием, но его окончание
не повторяет заблокированный поиск FOOD. GameLogger не фильтрует повторные INFO:
бессмысленные попытки исчезают в логике AI. INFO показывает границы рабочих
циклов, разговоров, недоступность действия и пробуждение решения при появлении FOOD;
DEBUG объясняет продолжение/выход из разговора, приоритеты и availability.

Проверки: SOCIAL/LEISURE против работы; 59/60 минут цикла на x1/x2/x4 и паузе;
сохранение production progress; минимальная/максимальная длительность разговора,
независимые выходы и forced; 180 минут без FOOD дают один реальный поиск и один INFO,
новая порция или освобождение брони вызывает второй поиск; появление FOOD не
прерывает TALKING/RELAXING; capacity=20 и projected fill; полная доставка до 20/20.
Предыдущие записи с SOCIAL=70, LEISURE=50, кухней 5 и нормой 60 минут описывают
историю разработки; текущие значения задаются этой записью и balance_config.gd.


## Balance/behavior pass: быстрые скорости

Обычный EAT доступен только при HUNGER >= EAT_MIN_HUNGER = 30; критический
голод сохраняет прежнее forced-поведение. SOCIAL и LEISURE накапливаются в пять
раз медленнее (делители роста = 5), веса остаются 80 и 75. Скорость удовлетворения
не меняется. RELAXING — committed action на RELAX_DURATION_MINUTES = 30:
низкий LEISURE не завершает его раньше, forced interrupt может прервать.
После завершения возникает normal decision point.

После 15 минут TALKING случайный выход допускается только при SOCIAL priority
ниже NEED_ACTION_THRESHOLD = 1000; более важное доступное действие также может
завершить разговор. Максимальная длительность остаётся 60 минут. Рабочий цикл
логируется как «завершил рабочий цикл», фактическое окончание смены —
«закончил работу». INFO категории LEISURE показывает начало/конец отдыха.

Скорости: pause, x1, x2, x4, x10, x20. Общий список GameTime используется UI и
движением. GameTime обрабатывает каждую пересечённую минуту и фазу, даже при
большом шаге; длительности проверяются через >=, без специальных веток быстрых
скоростей. Пауза замораживает игровое время и действия.


## Normal AI: ranked weighted random

Utility и selection — отдельные уровни. Need priority остаётся value *
effective_weight, WORK_PRIORITY остаётся 7000. Сначала собираются реально
доступные EAT/REST/SOCIAL/LEISURE/WORK; нет FOOD, собеседника или работы —
вариант отсутствует. HUNGER < 30 исключает EAT. NEED_ACTION_THRESHOLD = 1000
сохраняется для обычных личных действий. Проверка доступности не резервирует
ресурсы и не назначает HaulJob. Единственное сообщение о недоступной еде
сохраняет event-driven блокировку до изменения мира.

max_priority = max(available priority)
threshold = max_priority * UTILITY_CANDIDATE_RATIO (0.75)
candidates: priority >= threshold
shifted = max(priority - threshold, 1.0)
random_weight = pow(shifted, UTILITY_RANDOM_EXPONENT) (2.0)

Weighted random выбирает по random_weight среди кандидатов. Хорошие варианты
выбираются чаще; слабые ниже cutoff никогда. Каждый DecisionController имеет
свой seeded RNG (начальный seed от resident ID), независимый от RNG социальных
вариантов и генерации жителей. Тесты могут явно задать seed. Critical hunger,
critical fatigue, forced и обязательное ночное расписание обходят selector.
Начатые действия не пересматриваются из-за обычного роста Need. После выбора
WORK расписание запускает движение без второго случайного выбора.

INFO начала еды, разговора и досуга содержит текущую Need и priority; выбор
работы содержит priority=7000. DEBUG показывает max, threshold, кандидатов,
shifted, random_weight, исключения и selected. Полная картина не идёт в INFO.

SLEEP_SOCIAL_GROWTH_MULTIPLIER = 0.2 и SLEEP_LEISURE_GROWTH_MULTIPLIER = 0.2
дополнительно замедляют существующий рост во сне в пять раз, сохраняя ненулевой
рост и дробные единицы. Остальная sleep-логика не меняется.

Проверки: формула/cutoff, одиночный и пустой pool, воспроизводимость одинакового
seed, разные seed и статистика 10000 seed, исключение недоступных вариантов,
critical/forced без расхода RNG, INFO/DEBUG и ненулевой замедленный рост во сне.


## AI/behavior pass: прогулки, позиции и EAT response curve

Дубликат «Фёдор: выбрал работу» на 07:14 воспроизведён: decision_count вырос
на 1, INFO был записан дважды — DecisionController и ResidentScheduleController.
Теперь выбор логирует только DecisionController, расписание сообщает команды
ночи и реальные смены Activity. Это исправление владельца события, без фильтра
логов и debounce. При совпадении minute/action completion с границей фазы normal
решение ждёт phase_changed: расписание уже должно знать новую фазу.
Реальные две normal decision point также были возможны у свободного жителя,
когда idle deadline совпадал с phase_changed: оба подписчика запрашивали выбор.
На такой границе решение принадлежит фазовому событию, что проверено регрессией.

WANDER — обычный fallback в том же UtilitySelector, priority=500, radius=100,
stay=10 игровых минут. Это прогулка с последующей стоянкой, не LEISURE и не
снижение SOCIAL. WanderTarget содержит ID и позицию кандидата; источник цели
внедряется отдельно, сейчас выбирает точку внутри открытого 2D-поля. Позже этот
источник заменят Points of Interest. Полноценная POI-система не реализована.
Движение и стоянка — этапы одного действия, завершение стоянки даёт одну новую
normal decision point. Fallback уступает дневному расписанию, ручной команде
утром/вечером и ночи/forced. Стоящий IDLE-участник прогулки может принять разговор.

ConversationGroup имеет постоянный center, индивидуальные positions и свободные
слоты. Новые участники получают свободный слот, существующие не перестраиваются.
CONVERSATION_POSITION_RADIUS=64; дополнительные кольца не ограничивают число
участников. SocialController передаёт команду выравнивания через сигнал временному
представлению; короткое визуальное выравнивание не завершает SOCIAL намерение и
не создаёт decision point. Пауза/скорость применяются как к остальному движению.
SOCIAL=0 не запрещает принять приглашение, механики отказа нет.

Need value и Action utility различаются. HUNGER остаётся 0..100 и сохраняет
свой weight. Только EAT получает response curve:
normalized = (HUNGER - EAT_MIN_HUNGER) / (100 - EAT_MIN_HUNGER)
eat_utility = EAT_MAX_UTILITY * pow(normalized, EAT_UTILITY_EXPONENT)
EAT_MIN_HUNGER=30, EAT_MAX_UTILITY=10000, EAT_UTILITY_EXPONENT=2.0.
Ниже 30 EAT недоступен; на 30 доступен с utility=0, поэтому обычный WANDER
привлекательнее. HUNGER 50/70/90 даёт примерно 816/3265/7347. Critical hunger
100 обходит selector как прежде. SOCIAL/LEISURE/FATIGUE и WORK_PRIORITY не меняются.
UtilitySelector остаётся прежним: cutoff .75, shifted utility, exponent 2, seeded
weighted random. INFO начала еды и DEBUG показывают именно nonlinear utility.

Регрессии: один work choice/log на 07:14; одно normal решение после окончания
действия и при совпадении с 07:00; обязательная ночь без RNG; достижимость и
длительность WANDER без снижения Need; четыре разных физических позиции
разговора и стабильные слоты; нелинейная EAT в cutoff и forced hunger.


## Player Control Layer — первое управление профессиями

Игрок не только наблюдает: управление жителями — одна из основных частей игры.
ЛКМ выбирает одну ссылку ResidentData в ResidentSelection; голубое кольцо только
отображает этот выбор. Другой житель заменяет выбор, пустое поле/«Закрыть» снимает.
UI потребляет свои клики, работает на паузе, читает актуальные данные: имя,
профессия, Activity, текущий intent/action, HUNGER/FATIGUE/SOCIAL/LEISURE.

ResidentCard отправляет assign_profession(resident_id, profession) в PlayerControl.
Этот simulation API проверяет ID/существующую Profession и назначает work_location_id:
NONE → пусто, PORTER → склад, GATHERER → хижина. UI не меняет ResidentData напрямую.
Назначение постоянно и применяется к доступной работе на следующей normal decision
point; оно не является forced interrupt, не телепортирует и не запускает работу
немедленно. Все жители используют одинаковые динамические проверки роли.

Личное committed action, сон и его движение продолжаются. Начатый рабочий цикл
сохраняет исходную пару profession/location до безопасного завершения; производство
считает только реально WORKING у здания и не теряет building production_progress.
Новое назначение уже видно в ResidentData/UI, но следующий цикл старой профессии
не начинается. Если профессия изменилась на пути к старой работе, маршрут может
закончиться, но недействительный рабочий цикл не запускается — новая decision point.
Начатый HaulJob завершается с обеими бронями/грузом по прежним правилам. После
доставки работник снова проходит DecisionController с актуальной профессией.
Critical survival остаётся сильнее и сохраняет прежнюю отмену/выгрузку.

LogisticsController хранит задачи независимо от Степана; все жители зарегистрированы.
Существующий единственный физический executor передаётся фактическому claimant
только между рейсами. Назначение PORTER любому жителю работает; лимитов профессии
в UI нет. Параллельные рейсы нескольких носильщиков в этот шаг не добавлены:
пока executor занят, другой работник не начинает второй рейс. claim_best_job,
брони и формулы срочности не меняются. В дальнейшем каждый executor может стать
отдельным исполнителем при общей коллекции задач.

На этом шаге появилась первоначальная заготовка PlayerOrder. В следующем
согласованном шаге она заменена двумя отдельными понятиями PlayerCommand и
ResidentAssignment; player_order.gd удалён. Текущая иерархия и lifecycle описаны
ниже в разделе «PlayerCommand и контекстные взаимодействия». Profession остаётся
длительной ролью, не командой и не поручением.

WANDER INFO сообщает начало и завершение прогулки, включая отмену; DEBUG содержит
цель и причину прерывания. Координаты не идут в INFO. WANDER_PRIORITY=500,
WANDER_RADIUS=100, WANDER_STAY_MINUTES=10, UtilitySelector, Needs и формулы
production/logistics не изменены.

Проверка вручную: запустить main.tscn, выбрать любого жителя, сменить профессию
в выпадающем списке карточки. Shift+3 переводит в рабочий период; новая профессия
учитывается на подходящей decision point. NONE убирает профессиональную работу;
GATHERER открывает хижину; PORTER — доставку. Смена роли во время рабочего цикла

## PlayerCommand и контекстные взаимодействия — 2026-10-06

Это изменение заменяет прежнюю заготовку PlayerOrder: player_order.gd удалён.
Теперь два разных понятия. PlayerCommand — немедленный MOVE_TO, один ACTIVE

ResidentAssignment — отдельные данные с QUEUED/ACTIVE/SUSPENDED/COMPLETED/CANCELLED;
На этом первоначальном шаге конкретные типы и исполнение ещё не добавлялись.

## 2026-10-06 — реальные ResidentAssignment: EAT_AT_TARGET

ResidentData.assignments — собственный хронологический список данных поручений.
ResidentAssignment содержит id, resident_id, type, target (WorldLocation ID кухни),
state и importance. Единственный реализованный type — eat_at_target. States:
QUEUED / ACTIVE / SUSPENDED / COMPLETED / CANCELLED. Importance LOW/NORMAL/HIGH
предусмотрена, default NORMAL; сейчас ни один уровень не влияет на utility.
Завершённые и отменённые записи остаются в списке как простая история; кандидаты
берутся только из QUEUED. Порядок хранится для будущего UI, не означает FIFO.

PlayerControl.add_assignment(resident_id, assignment) проверяет владельца, тип,
существующую FOOD-кухню и уникальность ID; добавляет в конец без decision point
и без прерывания текущего committed action. cancel_assignment(resident_id, id)
отменяет queued/active поручение; активная еда очищается обычным исполнителем,
бронь снимается, уже съеденная FOOD не возвращается. UI списка пока нет.

ResidentAssignmentController каждого ResidentRuntime проверяет target и собирает
обычные action candidates для DecisionController. Они вместе с WORK/EAT/REST/
SOCIAL/LEISURE/WANDER проходят существующий UtilitySelector, без второго scheduler.
ASSIGNMENT_BONUS = 3000 — временный одинаковый бонус из balance_config.gd:

    normalized = (HUNGER - 30) / 70
    base_action_utility = 10000 * pow(normalized, 2)
    assignment_utility = base_action_utility + 3000

HUNGER < 30 исключает EAT_AT_TARGET, как обычную EAT. Cutoff 0.75, shifted utility,
exponent 2 и seeded RNG не изменены. Бонус повышает привлекательность, но поручение
может проиграть другому доступному кандидату. Список кандидатов стабильно сортируется
по ID поручения: место в хронологическом списке не даёт бонус и не меняет RNG-pool.
Бонус относится только к selector utility, не к приоритету MOVE_TO: underlying eat
intent сохраняет обычную base utility и существующие правила расписания/forced AI.
Новая жёсткая иерархия assignment vs critical не вводится.

Контекст кухни: «Идти к» — PlayerCommand; «Поесть здесь» — поручение. Второй пункт
enabled даже без еды: постановка поручения и доступность action candidate различны.
Нет FOOD / временно отсутствует позиция → QUEUED и нет кандидата, без retry cooldown
или нового polling. Доставка/освобождение FOOD использует существующий availability
signal: свободный голодный житель получает одну normal decision point, занятый
продолжает действие. Временное отсутствие позиции учитывается при следующем
обычном решении; отдельный таймер повторного поиска не добавлен.

Выбор → ACTIVE → reserve_out в конкретной target kitchen → обычный eat intent →
обычный путь → take_reserved при начале EATING → 30 минут постепенного уменьшения
hunger → COMPLETED до единственного нового decision point. Другая кухня не подменяет
цель. ResidentNeedsController предоставляет общий исполнитель и сигналы eat_started /
eat_outcome; отдельной еды, таймера или формулы удовлетворения для поручений нет.

До еды временно невозможная цель/бронь возвращает поручение в QUEUED с освобождением
собственной брони. Удалённое BuildingData в реестре означает окончательную невозможность
и CANCELLED; отсутствие/перемещение визуальной позиции при сохранённых данных — временное.
PlayerCommand использует прежний forced cleanup: ACTIVE → QUEUED, бронь освобождена,
consumed FOOD не возвращается, поручение не считается выполненным. После завершения
команды оно снова участвует в normal decisions. Остальные forced/critical правила
сохранены: прерванная еда requeued; если critical hunger усилил уже начатую еду в той
же кухне, успешное завершение этой же еды выполняет поручение.

PlayerCommand остаётся немедленным абсолютным управлением, один active, новый заменяет
старый. ResidentAssignment — сохраняемое предложение normal AI, не приказ и не FIFO.
SUSPENDED оставлен для будущего; сейчас прерванное выполнение возвращается в QUEUED.

Логи: PLAYER добавление; ASSIGNMENT начало/успех/отмена/прерывание; временная
недоступность только DEBUG без искусственного INFO rate-limit. Новые тесты
test_resident_assignments.gd проверяют список, бонус/importance/порядок, seeded
weighted выбор, точную кухню, event availability, shared meal, PlayerCommand cleanup,
постоянное/временное исчезновение цели и API отмены.


## 2026-10-06 — локальная совместимость critical EAT

Critical hunger не игнорируется: HUNGER=100 по-прежнему проходит существующий
critical bypass. ResidentNeedsController сначала определяет конкретный способ еды.
Уже начатая/оплаченная EATING сама является решением; другую кухню в этот момент
не выбираем. На пути выбирается первая подходящая FOOD-кухня в существующем порядке
реестра. Это прежняя политика concrete target selection, без нового distance score.
Собственная действующая бронь учитывается как доступное решение, даже когда
get_available_amount=0: она уже принадлежит текущему eating flow.

is_current_eat_compatible проверяет MOVE_TO/eat, идентичность принятого current
intent, конкретное BuildingData кухни и стадию исполнения. На пути необходимы
действующая собственная бронь и неизменившаяся позиция цели; после начала еды
используется _meal_active, включая синхронные сигналы при take_reserved.
Совместимость применяется к EAT_AT_TARGET и обычному autonomous EAT одинаково.

Совпадение → retain_current_as_critical сохраняет прежний intent и защищает его
существующим critical level 200 без forced_interrupt/intent_changed/реактивации.
Pending intent также сохраняется. Assignment остаётся ACTIVE; одна reservation,
один take_reserved, исходный таймер, один приём пищи. Успешное завершение этого
же flow переводит поручение в COMPLETED. INFO merge испускается на critical
transition, не каждый tick. Существующий DecisionController предотвращает повторы.

Другой concrete target на пути → обычное создание critical EAT и прежний cleanup:
поручение прежней кухни QUEUED, его бронь освобождается, новая кухня получает свою
бронь. Поручение не ретаргетится и не считается выполненным едой в другой кухне.
PlayerCommand как раньше немедленно прерывает и merged EAT: поручение QUEUED,
неиспользованная бронь освобождается, consumed FOOD не возвращается.

Это локальное compatibility rule, не новая hierarchy critical vs assignments.
UtilitySelector, ASSIGNMENT_BONUS, importance/порядок/duplicate assignments,
PlayerCommand, thresholds, hunger formula, meal duration, контекстное меню и
reservation model не изменены. Sleep/fatigue merge и новые типы поручений не добавлены.
Пока EAT_AT_TARGET — единственный тип поручения: прежнее forced поведение для
несовместимой деятельности проверяется на non-eat committed action RELAXING.
Тест test_critical_eat_compatibility.gd покрывает same/different target, оплаченный
приём пищи, autonomous EAT, сохранение pending и брони, completion, отсутствие
дубликатов и PlayerCommand; прежний полный test suite также обязателен.


## 2026-10-06 — поручение как отдельный экземпляр желаемого результата

ResidentAssignment представляет один экземпляр результата. Если результат достигнут
независимо от assignment-механизма, одно подходящее ожидающее поручение может быть
выполнено. Пока это реализовано только для EAT_AT_TARGET, без универсального framework.
ResidentNeedsController.eat_outcome передаёт конкретный target kitchen ID вместе с
intent и outcome. Только completed после успешных 30 минут еды запускает matching;
путь, reservation, начало еды, ошибка или interrupt не являются результатом.

ResidentAssignmentController._on_eat_outcome сначала обрабатывает поручение, связанное
с данным ACTIVE eating flow, и не запускает дополнительный поиск для этого события.
Если flow не связан с ACTIVE assignment, _complete_one_waiting_eat находит первую
хронологически добавленную EAT_AT_TARGET той же кухни в QUEUED/SUSPENDED и завершает
только её. COMPLETED/CANCELLED и другие targets пропускаются. Совпадение — по ID
конкретного места, не по названию, типу здания или координатам.

Один успешный приём пищи закрывает максимум один экземпляр поручения. Дубликаты
сохраняются как отдельные единицы работы; порядок добавления используется только
как deterministic completion tie-breaker, не меняет utility, importance или выбор
UtilitySelector. Независимое завершение пишет один INFO «поручение выполнено
независимо — Поесть здесь»; ACTIVE completion сохраняет прежний лог без второго.
Critical merge, PlayerCommand, eating/reservations/needs и availability не изменены.


## 2026-10-06 — TALK_TO: поручение на конкретного собеседника

TALK_TO хранит конкретный resident_id в ResidentAssignment.target. Пункт «Поговорить с …»
в контекстном меню другого жителя добавляет QUEUED-поручение через PlayerControl, не прерывая
текущее действие. Самому себе такое поручение дать нельзя. UI не управляет разговором.

Доступный TALK_TO участвует в обычном UtilitySelector с utility SOCIAL + ASSIGNMENT_BONUS
(3000). Порядок списка не влияет на utility. Временно занятый собеседник исключается из
кандидатов, поручение остаётся QUEUED; удалённый собеседник означает CANCELLED.
Изменения доступности уведомляют ожидающих жителей событиями, без retry cooldown.

Исполнение использует существующие движение SOCIAL, ConversationGroup и правила TALKING.
SOCIAL=0 не мешает принять разговор. Поручение выполняется после MIN_CONVERSATION_MINUTES
(15) непрерывного совместного присутствия жителя и конкретной цели в одной группе.
Время начинается заново при выходе/повторном входе цели; общий возраст группы не заменяет
совместное время. После COMPLETED сам разговор может продолжаться.

Независимый разговор тоже может выполнить одно подходящее поручение. ACTIVE-поручение
имеет право на свой результат первым; иначе закрывается самое старое подходящее QUEUED
(или ожидающее SUSPENDED) по порядку добавления. За один разговор жителя закрывается максимум
один экземпляр; дубликаты остаются отдельными поручениями и не удаляются.

Ранний выход цели или прерывание PlayerCommand/critical AI возвращает незавершённое
исполнение в QUEUED. Уже достигнутый COMPLETED не откатывается. Резервирования еды,
critical EAT merge, UtilitySelector, веса и общая иерархия управления не изменяются.
Отношения, отказ от приглашений и отдельный таймер assignment-разговора не добавлены.

Данные поручения, генерация кандидатов и bonus уже общие; новый слой исполнителей

FOOD reservation, eating flow, ConversationGroup, временные проверки и utility

## 2026-10-07 — resident-owned строительный workflow

ResidentBuilderController — отдельный controller каждого runtime, не глобальный scheduler.
Он получает реестр зданий, позицию через Callable, часы и IntentController. Фазы:
GOING_TO_SOURCE, CARRYING_TO_SITE, GOING_TO_SITE, BUILDING. Все стадии одного task
сохраняют слот; завершение рейса после смены профессии, обычная граница рабочего цикла,
нет материалов, удаление цели и forced cleanup освобождают его. Site score не сравнивается
с needs: сначала выбирается WORK=7000 существующим UtilitySelector.

Строительные reserve_in живут в BuildingInstance отдельно от functional ResourceContainer.
reserve/deliver/release контролируют непокрытый дефицит. Прямое add_delivered_material
также не может занять место, обещанное резервом. Доставки не являются HaulJob; исходящий
резерв источника остаётся существующим ResourceContainer.reserve_out/take_reserved.
Inventory теперь допускает одну FOOD или WOOD, но не >1 unit. GroundResource visual/target
показывает фактический тип, pickup на земле не реализован.

В BUILDING учитываются реально проведённые у стройки work-minutes при WORKING. Вклад
записывается в BuildingInstance на границе 60 минут либо при прерывании (частичный вклад).
Этот подход сохраняет worker cycle как committed action и уже выполненную работу при
critical/PlayerCommand. После полного цикла ровно одна normal decision point.

Источники/стройки уведомляют controller локальными availability_changed/construction_changed;
недоступный источник не ищется заново на каждой idle decision point. При всём дефиците
в пути выбран простой вариант: выйти из task, освободить slot, без waiting loop.
Изменение availability не прерывает обычное личное действие. Исчезновение registry target
проверяется также у активного executor на игровых минутах/arrival, это проверка валидности
исполнения, не polling поиска новой работы. Синхронные interrupts во время reserve/pickup/
delivery завершают cleanup после атомарного обновления физического владения, без потери WOOD.

Main подключает новый BUILT instance к прежним системам один раз по state signal: kitchen
к FOOD availability и логистике; storage к ресурсам/workplace; hut к production/логистике.
GathererProduction обслуживает дополнительные хижины в том же minute observer перед AI,
с прежней формулой. Logistics принимает дополнительные FOOD routes, оставаясь единственным
porter executor. PlayerControl.register_building регистрирует workplace, сохраняя прежний
default workplace; контекстное employment назначает конкретное завершённое здание.
Дома получают обычное взаимодействие «Идти к», housing mechanics не добавлены.

- Default/invalid home безопасен. Demolition, auto-fill, beds, quality, penalties,
  семьи и housing AI отсутствуют; эти механики будут отдельными этапами.

### Ordinary night sleep использует актуальное жильё (2026-10-07)

Обычный ночной сон использует текущую housing связь.
Schedule получает существующий общий buildings Array; валидирует конкретный ID,
BUILT, HOME и housing_capacity > 0. Позиция — WorldLocation дома, либо position
экземпляра без visual mapping (центр footprint); отдельного HousingController нет.

Home читается при активации обычного ночного намерения, включая pending после еды
или перевозки. После начала пути сохраняются concrete target и ID только текущего
execution; reassign/clear не reroute-ят и не будят. Если цель исчезла к прибытию,
житель спит снаружи на достигнутом месте, без зависшего маршрута.

Без валидного дома — stationary night_outdoor intent и SLEEPING на текущем месте.
Утром очищаются как маршрут, так и stationary intent. Resume той же ночной фазы
не пересоздаёт committed sleep. Локальный intent_changed обрабатывает pending
активацию до visual executor; forced_interrupt очищает ownership для нового решения.

Critical fatigue и PlayerCommand сохраняют существующие forced правила. Расписание
23:00–06:00 и recovery не меняются. Capacity не является sleep slot; несколько
жителей спят в одном доме. Beds, quality и outdoor penalties остаются будущими.

### Стартовые HOME используют обычный building lifecycle (2026-10-07)

Main создаёт четыре plain BuildingInstance с общей HOME definition и state BUILT.
IDs home_stepan/home_anna/home_fedor/home_marina стабильны; home_location_id —
единственная связь resident ↔ home, без ownership и второго реестра.

Общий _show_building создаёт BuildingView2D/WorldLocation как для starting setup,
так и для player placement. BUILT экземпляр подключается через ту же
_activate_completed_building, что завершённая стройка. HOME subtype/StarterHome
не добавлены; обычный display_name «Дом» берётся из существующей definition.
Отдельная устаревшая сцена/скрипт домашнего визуала удалены вместе с home_names
и отдельным setup path. Все normal selection/card/housing/sleep/collision queries
используют тот же Main.buildings. Construction/AI/recovery behavior не меняются.

### Sleep quality — числовой snapshot конкретного действия (2026-10-07)

ResidentData.current_sleep_quality — локальное текущее execution state, не
постоянная характеристика дома. start_sleep(quality) задаёт число перед SLEEPING;
выход из SLEEPING очищает snapshot до outdoor default. Никакого SleepController,
frame lookup housing или sleep-quality UI нет.

Schedule вызывает start_sleep: home arrival проверяет сохранённый concrete
_sleep_home_id, задаёт HOME_SLEEP_QUALITY=1.0. Outdoor fallback задаёт 0.6 сразу;
исчезновение committed дома до arrival тоже даёт 0.6. Изменение home_location_id
во время пути/сна не меняет context/quality текущего action. Critical fatigue
в ResidentNeedsController вызывает start_sleep(OUTDOOR_SLEEP_QUALITY), даже с домом,
сохраняя on-spot путь, forced priority и прежнее условие пробуждения FATIGUE<=20.

NeedDynamics сохраняет базовый FATIGUE_RATES[SLEEPING]=-30 единиц при
UNITS_PER_POINT=60, умножает только эту rate на numeric snapshot. Fractional
accumulator принимает float rate, сохраняя дробное восстановление между минутами;
не округляет multiplier до одного из двух режимов. Awake/hunger/social/leisure
rates и формулы остаются прежними. 60 минут: home −30, outdoor/critical −18.
В будущем caller сможет вычислить quality как housing × weather × furniture;
сейчас этих систем нет. DEBUG quality логируется только при старте действия.


### Навыки: ResidentData XP и derived level (2026-10-07)

ResidentData владеет private-convention dictionary SkillType → integer XP.
get_skill_xp/get_skill_level/add_skill_xp — общий API без эффектов профессий.
Отдельный mutable level не хранится. Level считается из balance constants
SKILL_XP_PER_LEVEL=10, MAX_SKILL_LEVEL=10; XP не ограничен уровнем 10.
Нулевые/отрицательные additions отвергаются без события.

Начисление стоит только на successful completion: DecisionController завершает
gatherer cycle и использует profession snapshot начатой работы; BuilderController
выдаёт XP после полного цикла/cleanup, но не при partial flush; PorterHaulExecutor
выдаёт XP после delivery и завершения committed HaulJob. Никаких начислений
в production output, builder transport или building completion нет.

skill_changed(skill, amount, previous_level) сообщает изменение XP. ResidentRuntime
пишет DEBUG XP и INFO только при level increase; ResidentCard подписывается на
выбранного жителя, отключает старую подписку и обновляет skills label по сигналу
или selection change. Skills не обновляются через frame refresh. Signal payload
previous_level — временное значение для logging, не второе mutable level state.

Минимальная data-модель допускает будущую замену progression и использование
уровня любыми системами без profession coupling. Сейчас никакие gameplay
потребители навыков и placeholder modifiers не добавлены.


### Behavior base values plus modifiers; traits как первый источник (2026-10-07)

ResidentModifiers — небольшой stateless resolver с явно типизированным Action
(WORK/EAT/SOCIAL) и узкими API для threshold, movement speed, selector ratio/exponent.
Consumer спрашивает effective value, не знает конкретных trait IDs. Definitions
(семь IDs/имена/conflicts) живут в TraitType, numeric contributions — только в
balance_config. Resource-only prototype definitions и неподдерживаемый stubborn
удалены; отдельной trait effect scripting/registry/graph системы нет.

ResidentData.traits — список enum IDs; add_trait отвергает duplicate/conflict без
auto-remove, remove_trait безопасен для отсутствующего ID. Обе успешные операции
эмитят traits_changed. Generator выбирает первую черту seeded RNG, исключает
её/конфликт, выбирает вторую и сохраняет результат. Степан также получает пару
через этот generator; Factory допускает явно заданные списки для tests.

Multipliers: effective = base × product(contributions); threshold = base + sum,
с semantic clamp. Resolver может позже включить mood, skills/experience, health,
weather, settlement events, policies, temporary states без переписывания callers.
Пустых providers сейчас нет. Traits преимущественно модифицируют существующие
системы: SOCIAL/WORK attractiveness, EAT attractiveness/minimum, physical movement,
normal weighted selection. Need state/base weight, production/work timing и XP
не меняются. EAT curve принимает optional minimum, default сохраняет прежнюю
формулу; обычный GLUTTON использует effective threshold 20 и utility ×1.2.

UtilitySelector остаётся generic: evaluate принимает optional ratio/exponent с
fallback base constants. DecisionController применяет effective utility до max/
cutoff/weights и передаёт effective selector параметры. DEBUG включает оба значения.
Critical/forced/mandatory night sleep/PlayerCommand bypass не меняется. Assignment
utility/bonus и targeted EAT threshold остаются прежними: utility multipliers
применяются к ordinary action candidates, не к явным поручениям. TALK_TO availability
не зависит от INTROVERTED. Work score на уровне site/delivery не модифицируется.

ResidentView использует один effective movement speed для любых источников intent.
ResidentCard подписывается traits_changed только выбранного жителя, без polling.
Регрессионные harnesses явно убирают traits через API, чтобы проверять базовое
поведение независимо от starting generation. Новые trait tests проверяют effects
с явно заданными чертами и настоящие маршруты/critical contexts.


### Directed relationships и границы будущей social architecture (2026-10-07)

Реализован только слой A: Directed opinion — субъективное A→B. ResidentData
владеет sparse dictionary stable other ID → ResidentRelationship. Минимальные
поля объекта: other_resident_id/opinion; никаких future placeholder fields.
OPINION_MIN=−100, MAX=100, NEUTRAL=0 централизованы в balance_config.
get_opinion/get_relationship/has_relationship не создают record. set/change
создают его только при фактическом изменении; neutral set(0)/change(0) без
record — no-op. Self/empty writes возвращают false, reads neutral/null.
set/change возвращают true только когда эффективное мнение изменилось.

Record setter clamp-ит и эмитит opinion_changed только при изменении. ResidentData
передаёт этот локальный сигнал как relationship_changed(other_id), включая запись
через полученный data object. Второй resident не вызывается, обратное мнение не
синхронизируется. Если будущее событие влияет на обоих, caller сам применит два
разных delta. Existing record может сохраняться при возврате к neutral.

ResidentCard читает current roster через PlayerControl.get_residents, подписывается
только на relationship_changed выбранного resident и отключает старую подписку.
Локальный PlayerControl.residents_changed сообщает об изменениях при setup
population; новый global bus/removal system не нужен. Отсутствующие targets
сохранённых records в карточку не попадают. Frame refresh отношения не опрашивает.

Долгосрочные слои B–G пока только архитектурное направление:
- B. Compatibility — более стабильная pair-level характеристика, отдельно от
  opinion; её будущая симметрия ещё не определена.
- C. Social memories — причины/события, которые позже изменят opinion через
  change_opinion; объяснимые contributions возможны, сейчас их нет.
- D. Relationship states — будущие semantic directed states (friend/rival/etc.),
  без автоматического вывода FRIEND из opinion=60 на этом этапе.
- E. Shared events — отдельные события с event_id/participants/time/data; будущие
  references из relationships/memories, без копирования общего текста в обе связи.
- F. Genealogy/kinship — объективная family structure, не subjective opinion и
  не opinion tags. Parent/child связь может сосуществовать с opinion −40.
- G. Chronicle/biography — будущее представление значимых life/shared events.

Эти слои не реализованы; placeholder controllers/fields и compatibility score
не добавлены. Нет automatic conversation opinion, decay, social AI modifiers
или случайных initial opinions. Существующие social execution/selector/modifiers
не меняются. Current API/data даёт отдельное место для будущего directed metadata.


### Directed trait preferences вместо отдельной symmetric compatibility (2026-10-07)

Три понятия разделены: traits — «какой resident сам»; trait preferences — «какие
чужие traits ему нравятся»; opinion — stored directed history-based attitude.
Ранее обозначенный будущий compatibility concept сейчас заменён личными directed
preferences; отдельной symmetric score/matrix системы не реализуется. Opinion
не получает initial delta, записи и drift от preference calculation.

ResidentData владеет Array[TraitType] liked_traits/disliked_traits. API has/add/remove
валидирует IDs, дубликаты и пересечение lists; не auto-remove противоположный taste.
Own traits допустимы в обоих списках (по отдельности). Opposite character traits,
например SOCIABLE/INTROVERTED, могут нравиться одновременно: конфликты характера
не являются конфликтами личных вкусов. Успешная mutation эмитит trait_preferences_changed.

TraitPreferenceResolver — stateless calculation current A tastes + current B traits.
Score = sum(+10 liked contributions, −10 disliked); no artificial clamp. Ни ID→score
storage, ни pair cache, ни full trait×trait matrix нет. Изменение A tastes или B traits
сразу отражается в следующем вычислении. Self/null безопасно даёт 0. Этот derived
contribution позже может использоваться social attraction, events, opinion formation,
но сейчас gameplay consumers его не используют.

Generator имеет отдельный preference RNG (seed xor local salt), чтобы сохранить
старую sequence собственных traits/имён/needs. Два likes и один dislike выбираются
без replacement из TraitType catalog; новые IDs автоматически доступны этому
алгоритму. Результаты сохраняются как обычные mutable data. Starting Степан тоже
получает prefs из того же seeded architecture. Factory имеет optional explicit
liked/disliked arguments и копирует их через validated API; old callers/default
ResidentData имеют безопасные пустые lists. Save/serialization сейчас отсутствует.

Card подписывается на preference changes выбранного resident и на traits_changed
остальных current roster targets. Selection/roster change отключает старые target
subscriptions, rebuild-ит их и пересчитывает score label. Opinion signal по-прежнему
обновляет directed opinion presentation; preferences/opinion остаются независимыми.
No frame polling. Labels используют catalog display names; effect values скрыты
в preferences block, derived score допустим в prototype relationship block.

Future social systems могут комбинировать stored opinion + derived preference +
memories + mood + context + shared events. Эти слои, romance/friendship/genealogy
и automatic preference/opinion changes сейчас не добавлены.


## Social Events: mechanics до narrative (2026-10-08)

SocialEventService — один локальный сервис, подписанный на existing lifecycle
signals. Контексты WORK/MEAL/CONVERSATION не создают subclasses. Маленькие start
notifications не меняют существующие action execution/interrupt semantics.
Рабочий roll происходит каждый цикл Gatherer/Builder. Porter не получает
искусственную social location: его transport не является stationary work cycle.

Нет symmetric compatibility. Derived directed social attitude = clamp(stored
opinion + derived trait preference, −100,100). Независимые реакции каждого
участника рассчитываются из snapshot обоих attitudes; existing change_opinion
применяет −1/0/+1 и сохраняет sparse/clamp semantics. Это намеренное развитие
предыдущего opinion foundation: теперь разговор МОЖЕТ менять opinion именно
через SocialEvent, не через timer/обычный TALK_TO completion.

Semantic pool queries existing state: active meal building, committed work
location, builder BUILDING site, stationary conversation group. Building visitor
— участник активного разговора, центр которого внутри footprint; distance/radius
не используется. Просто движение или proximity не создаёт semantic membership.
Uniform partner selection не учитывает opinion/tastes, избегая social bubble.

Narrative entries — JSON data с optional filters и раздельными Feed/Diary strings;
код не знает story enums JOKE/ARGUMENT. Выбирается запись после реакции и opinion.
Пробуются обе orientation; одна запись = один equal-weight ticket, даже когда
подходят обе. Затем orientation выбирается равновероятно среди matching.
Нет specificity priority, base_effect, rarity или weights. No match безопасен.

Mechanics и presentation используют отдельные RNG streams: смена библиотеки
текстов/diary chance не влияет на следующие chance/target/reaction draws. В игре
оба RNG randomize; seed/injected RNG обеспечивают deterministic tests. Не вводится
общая global RNG architecture.

SocialEvent не обязан persist. Feed ephemeral, Diary optional per-participant
history, chance 20%; TEMPORARY истекает следующим утром по phase_changed,
KEY сохраняется. Feed Timer имеет real-time UI lifetime 12 секунд и limit 4,
не участвует в simulation. Diary changed обновляет карточку event-driven.
Diary ещё не future psychological memory: нет memory modifiers или opinion decay.
Gameplay feedback кроме directed opinion и presentation/history не вводится.
