# Личный дневник и воспоминания

Текущий контракт, 2026-11-03. Единственный источник записей — ResidentData.memories,
существующий MemoryStore. Отдельных DiaryEntry/diary_entries/утреннего TEMPORARY
cleanup больше нет. Название в интерфейсе — «Дневник». Save/load и перенос старой
запущенной сессии не реализованы и не требуются этим этапом.

## Данные и события

Запись хранит id/owner, text, created_minute, type/topic/tags, target, participants,
strength0…100, permanent, provenance, context и исходные/последние source IDs.
Дата/время вычисляются из created_minute по GameTime, второго календаря нет.
Чтения возвращают копии. Текст обязателен, рендерится один раз и не меняется при
усилении. Participants — entity refs, а не удерживаемые runtime Nodes.

Все новые записи каталога permanent:false. Каждый смысловой исход создаёт одну
запись; прежних независимых Diary/Memory бросков нет. Сохранены остальные мудлеты,
чат, cooldown, роли/условия, trigger probabilities и веса. Общая летопись остаётся
отдельным обязательным результатом каждого completed события. Изменившийся набор
бросков личных записей закономерно меняет последующий RNG последствий; AI/social/
opinion RNG не используются этой системой.

Существующий memory.add остаётся каноническим добавлением. Старые diary.add,
diary_main/diary_secondary, secondary_diary и diary_importance отвергаются каталогом.
EventTextRenderer и его грамматика/варианты общие для text, chat.say и летописи.

## Усиление и транзакция

memory.reinforce принимает owner, entry_id, expected_version, amount и chance.
ID и _version выбираются из того же binding записи. _version — внутренний
монотонный номер каждого изменения, общий генератор технических версий в классе
Store. Он различает также новое хранилище и remove+add старого ID; это не игровой
уровень и не дополнительная история событий.

prepare_reinforce не меняет Store. Перед commit executor повторяет проверку версии,
активности владельца и идентичности Store. _apply_event_update — тихая операция,
затем прежний coordinator фиксирует completed/cooldown и публикует changed.
Один occurrence не усиливает повторно. Устаревший/удалённый ID отклоняет весь пакет;
подбора другой памяти и повторного RNG нет. Два изменения одного destination в
одном событии отвергаются, не суммируются скрыто. Прямой reinforce использует ту же
подготовку, но сам по себе не является ledger дедупликации событий.

## Ночь: 23:00

MemoryStore.advance вызывается существующим ранним минутным callback Runtime.
Перед снимком событий ResidentEventFacts.advance_all актуализирует журналы обоих
участников: сначала подготовить всех, тихо применить всех, затем уведомлять.
Поэтому события не видят одну сторону до обслуживания, другую после. Маркер
последней ночи защищает от повторения и лишнего ослабления в полночь. При привязке
нового журнала не начисляется забывание за время до его существования.

Для каждой пересечённой ночи, в календарном порядке:

1. Слить смысловые повторы, permanent должен совпадать. Сохранить запись с наибольшим
   created_minute, при равенстве — лексикографически наибольшим ID. Её текст, ID,
   исходная дата и происхождение остаются. Сила=min(100,max(strength)+10*(count-1)).
2. Обычные записи ослабить на5, удалить при0. Permanent полностью пропускает decay.
3. Лимит=min(10+абсолютный день,50): день1→11,39→49,40+→50. Учитывать permanent,
   но удалять только обычные: слабейшие, затем старейшие, затем ID по возрастанию.
   Если одних permanent больше лимита, превышение сохраняется. Днём лимит не
   применяется. Слияние permanent-повторов по пункту1 сохраняет одну permanent
   запись; защита от decay/prune не запрещает это прямо заданное слияние.

Ключ смысла: type/topic, множество tags, target, множество participants, permanent,
provenance и смысловой context. Словарные ключи канонически сортируются. Текст,
силу, даты и технический ID самой записи не сравниваем. В context/provenance
игнорируются _event/_version, occurrence/source IDs, revision, служебные timestamps,
диагностика/debug и pride_moodlet_id; остальные поля сохраняют смысл. Target.id,
идентификаторы участников/рассказчика и incident_id не стираются: разные цели,
источники слуха или явно разные происшествия не смешиваются. Новые семантические
поля по умолчанию участвуют, отдельного mergeable или списка разрешённых типов нет.
Разные здания-цели — разные воспоминания; завершение строительства не исключено из
общего механизма слияния одинаковых записей.

Технические last_changed_minute/_version обновляются при мутации; даты старых
повторений отдельно не сохраняются. Обычная начальная сила0 допустима по диапазону
данных; удаление при ночном достижении0 выполняется общим алгоритмом. Если запись
сначала слита с повтором, применяется утверждённый порядок merge→decay→limit.

## Полная память в EventFacts

Факт memories имеет тип collection. EventFactCollection — неизменяемый снимок
проверенных JSON-записей, внутри страницы по256; он не держит Store/жителя/Callable.
Страницы возвращаются копиями. EventFacts.set_collection валидирует каждую запись,
не ограничивая количество записей и не отбрасывая хвост. Обычные JSON Array/Dictionary
по-прежнему ограничены256, глубина/AST и остальные проверки не увеличивались.

exists и select_one читают страницы в существующем evaluator. Для выбора проверяется
вся коллекция: одна запись с минимальным id/value, при равных ключах сохраняется
исходный порядок. Неизвестный кандидат не скрывается при select. У каждого
предиката остаётся прежний step/depth budget; длина полного журнала не превращается
в лимит первых элементов. Стоимость линейная числу проверенных записей; ранний
успех exists возможен по прежним правилам. Невалидная обычная Array>256 всё ещё
отвергается. Collection нельзя выдать за JSON-поле эффекта: его нужно запросить,
выбрав конкретную запись или проверив exists.

Снимки собираются и для личных/строительных триггеров. Для их явных bindings
сохраняется копия реестра идентичностей, без чтения всех контроллеров или копирования
потребностей/памяти остальных жителей.

## Интерфейс и проверки

Карточка подписана на тот же memories.changed, отключает подписку при смене выбора/
уничтожении. Показывает все сохранившиеся записи по датам, новые сверху, с игровым
временем и текстом. Порядок при одинаковой минуте стабилен. Отдельной копии истории
и скрытого архива удалённых записей нет.

test_event_catalog_content, test_warm_sympathy, test_social_quarrel, test_meal_events,
test_live_skill_events, test_construction_game_events, test_event_text_grammar и UI.
